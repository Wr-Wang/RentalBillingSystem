# 住宅房屋租赁收租结算系统 — 需求文档

> 详细设计请参见[详细设计文档](./详细设计.md)。

---

## 一、项目核心目标

构建一套专业的 **住宅房屋租赁收租结算系统**，以 BackgroundService + Cronos 为调度引擎，覆盖以下核心业务闭环：

```
基础支撑:
  ├── 组织架构(用户/角色/权限) → 菜单权限控制
  └── 审批工作流(0~N级)       → 合同变更/终止/减免等审批

业务闭环:
房源管理 → 合同签订 → 租金应收 → 多渠道收款 → 账务处理 → 催缴管理 → 报表统计
                                            ↑
                                      Cronos 定时调度
```

**一句话目标**：让公司能管房、管合同、自动算租金、收钱自动记账。

**适用市场**：中国大陆住宅租赁市场  
**会计准则**：CAS 21（企业会计准则第21号—租赁）

## 二、用户使用流程

### 2.1 核心业务流程

```
┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐
│  1.房源   │→│  2.合同   │→│  3.应收   │→│  4.收款   │→│  5.账务   │
│  管理     │  │  管理     │  │  计划     │  │  确认     │  │  处理     │
│  (座楼室) │  │ (签租约)  │  │ (自动生成)│  │ (多渠道)  │  │ (日记账)  │
└──────────┘   └──────────┘   └──────────┘   └──────────┘   └──────────┘
                                                   │
                                          ┌────────┴────────┐
                                          │  催缴管理        │
                                          │  (逾期→提醒→催缴)│
                                          └─────────────────┘
```

### 2.2 角色操作流程

**运营人员（日常操作）**：
```
登录 → 房屋管理(查看/导入) → 合同管理(新建/变更/续签) 
     → 租客管理(维护信息) → 催缴管理(查看催缴任务)
```

**财务人员（收租对账）**：
```
登录 → 仪表盘(今日收款/欠费) → 收款确认(审核到账) 
     → 银行对账(导入流水→匹配) → 会计凭证(审核)
     → 报表(收租率/欠费明细)
```

**审批人（各级主管）**：
```
登录 → 待审批列表(合同终止/减免/转租等) → 查看申请详情 
     → 通过/驳回 → 自动流转下一级或完结
```

**系统管理员（基础配置）**：
```
登录 → 组织架构(用户/角色) → 菜单权限分配 → 审批流程配置(级别/审批人)
     → 收费项目配置 → 税率配置 → 支付通道管理 
     → 调度任务管理 → 会计科目管理
```

### 费用配置 - 版本化调价（详细需求）

> 费用配置的添加/调价/停用/启用均需经过"预览→提交审批→审批通过后执行"的闭环流程。所有操作统一走 CONTRACT_FEE_CHANGE 审批类型。

#### 0. 统一审批流程

费用配置的所有变更统一经过以下流程：

```
填写表单（选择费项、金额、生效日期、原因）
  ↓
[预览变更] → 展示变更摘要、会计影响、补差明细
  ↓
确认 → 提交审批（CONTRACT_FEE_CHANGE）
  ├─ 有审批配置 → 走审批流
  └─ 无审批配置 → 0级自动审批
      ↓
审批通过 → 写入主表 + 生成补差 JE（如涉及已出账月份）
```

**预览展示内容**（费用调价/批量调价）：
- 变更摘要表：每项费用旧价→新价、差额、涨幅百分比、生效日
- 会计影响：D 1122 应收账款 / C 6001 主营业务收入、每月增减金额
- 补差明细：已出账月份按天分摊计算明细
- 未来月份：生效后各月预估值

**单条调价**：行内[调价]按钮路由到 `POST /{id}/feeadjust`，与批量调价共用同一审批端点

**停用/启用**：存入 `ApprovalFeeItems` 表（NewAmount=-1 标记停用、-2 标记启用），走相同审批流

#### 1. 有效期管理
- 每项费用配置必须有 `生效日期（EffectiveDate）`，可选 `到期日期（ExpiryDate）`
- 到期日期为 NULL 表示永久有效，无截止期限
- 同一合同同一种费用同一生效日期只有一条记录（UNIQUE 约束）

#### 2. 调价逻辑
- 调价不修改原有记录，而是将原记录标记到期 + 插入新记录
- **示例**：Rent 原价 ¥5,000，生效 2026-01-01，无到期日
  - 调价到 ¥5,050，生效 2026-07-01
  - → 原记录到期日更新为 2026-06-30（新生效日减1天）
  - → 新增记录：¥5,050，生效 2026-07-01，到期 NULL
- 删除操作不可用（历史记录需保留审计轨迹），如需停用可设到期日或标记 IsActive=false
- **新生效日必须大于原生效日**：若 newEff <= curEff，则原配置到期日 = newEff - 1 会小于原生效日，造成时间逻辑错误（如原 Eff=07-06，新 Eff=07-06 → 原 Exp=07-05 < Eff=07-06），前端和后端均需拦截

#### 3. 按天分摊计算
- 费用按 **当月实际天数 × 日金额** 计算，非整月生效时按天分摊
- **日金额 = 月金额 ÷ 当月总天数**
- **当月应收 = 日金额 × 当月生效天数**
- **跨月调价场景**：如 7 月 15 日调价，7 月应收 = 旧价 × 14天/31 + 新价 × 17天/31
- **同月内多次调价场景**：同一个月内有 N 条费用配置时，每条配置按覆盖天数分别分摊后汇总

##### 同月多次调价计算示例

6月份（30天），某费用项目有四条调价记录：

| 记录 | 月金额 | 有效日期区间 | 覆盖天数 | 分摊金额 |
|------|--------|------------|:-------:|:-------:|
| #1（初始） | ¥5,000 | 06-01 ~ 06-02 | 2天 | ¥333.33 |
| #2（调价） | ¥5,002 | 06-03 ~ 06-03 | 1天 | ¥166.73 |
| #3（调价） | ¥5,006 | 06-04 ~ 06-06 | 3天 | ¥500.60 |
| #4（调价） | ¥5,010 | 06-07 ~ 至今 | 24天 | ¥4,008.00 |
| **合计** | | **覆盖整月** | **30天** | **¥5,008.66** |

> 公式：每条记录分摊金额 = ROUND(月金额 / 当月总天数 × 覆盖天数, 2)
> 汇总：∑ 各条分摊金额 = 当月应收金额

#### 4. 前端展示
- 配置列表显示当前生效价格（`ExpiryDate IS NULL`）
- 列中增加"生效期"字段：`2026-01-01 ~ 2026-06-30` 或 `2026-07-01 ~ 至今`
- 点击行可展开查看该费用项的所有版本历史
- 操作列仅保留"调价"和"启用/停用"，不提供删除

#### 5. 前端提交预校验（日期冲突检测）

##### 5.1 业务规则
- 用户在调价弹窗输入生效日期后，**提交前**前端必须从数据库拉取该费用项目的全部历史配置
- 前端计算：旧配置到期日期 = 生效日期 − 1天，新配置生效日期 = 生效日期
- 检查：新配置的日期区间 `[生效日期, 永久)` 是否与任何已有配置的区间重叠
- 如果存在重叠 → 拦截提交，弹出错误提示，告知用户"该费用项目的生效日期与已有记录冲突"

##### 5.2 数据来源
- 使用已有后端接口 `GET /api/contractfeeconfigs/history` 获取某合同某费用项目的全部版本记录
- 返回数据结构包含：`id, amount, effectiveDate, expiryDate, isActive`

##### 5.3 校验算法（JavaScript，前端子实现）
```
获取该费用项全部历史版本（含当前生效记录）
排除"当前被到期"的那条配置（即当前 IsActive=true 且 ExpiryDate=null 的记录）
逐条检查：生效日期 < (已有配置的到期日期 ?? 9999-12-31) 是否为 true
  若 true → 重叠 → 拦截
  若全 false → 无冲突 → 放行通过
```

##### 5.4 交互表现
- 以费用项目为粒度分别提示，精确告知用户哪个费用项目冲突
- 冲突提示文案：`「{费用项目名称}」的生效日期 {日期} 与已有记录（{已有配置日期区间}）重叠，请调整生效日期`

##### 5.5 后端双重校验
- 审批回调中保留原有 `EnsureNoOverlappingFeeConfigAsync`（使用 SQL 标准区间交叉检查）
- 前端校验为第一道防线（提升用户体验），后端校验为第二道防线（数据安全）

### BillJob 账单生成闭环设计

#### 1. 设计目标

账单生成的源头统一为**记费项**（BillingJournal），所有收费（租金、费用、押金、补充收费）先生成记费项，再通过账单生成步骤将未出账的记费项聚合为账单。

```
收费事件 → 记费项(BillingJournal) → 账单生成 → DebitNote + DebitNoteItem
                                    ↑
                          查询 IsBilled=false 的记费项
```

#### 2. 记费项（BillingJournal）定义

每条记费项代表"某合同某费用某账期的一笔应收"，包含：

| 字段 | 说明 |
|------|------|
| 合同ID | 所属合同 |
| 费用项目ID | 指向 FeeCode（押金使用特殊内置 FeeCode） |
| 费用名称 | 生成时的快照 |
| 账期 | 该费用所属的月份（yyyy-MM） |
| 金额 | 该账期的应收金额 |
| 到期日 | 应收到期日 |
| 条目类型 | `Normal`(常规费用) / `Deposit`(押金) / `Supplementary`(补充收费) |
| 已出账标记 | `IsBilled`：是否已纳入账单 |
| 账单ID | 纳入的 DebitNote ID（出账后回写） |
| 出账时间 | 出账时间戳 |

> 实现方式：在现有 `ReceivablePlans` 表上扩展 `IsBilled`/`DebitNoteId`/`BilledAt`/`EntryType` 四个字段，不新建表。

#### 3. 房租及常规费用出账流程

以6月份房租5008.66为例（4条调价记录分摊合计）：

```
BillJob 执行流程:

Step01: 加载生效合同
Step02: 加载费用配置（含历史调价记录）→ 按FeeCodeId分组
Step03: 按天分摊计算 → 每个FeeCodeId算出一笔总金额
  └─ 创建 ReceivablePlan (Status=Pending, IsBilled=false)
  └─ 创建 Voucher + JournalEntry (借1122 / 贷6001)
Step04: 费用配置到期处理
  └─ 将当前房租费配置的 ExpiryDate 设为账期月末日
  └─ 创建新配置: 生效日期 = 账期次月1日, 金额不变
Step05: 生成账单（仅当有未出账记费项）
  └─ 查询该合同下所有 IsBilled=false 的 ReceivablePlan
  └─ 创建 DebitNote + DebitNoteItems（逐条写入）
  └─ 回写 ReceivablePlan.IsBilled=true, DebitNoteId=, BilledAt=
```

**费用配置自动续期**：
```
原房租配置:
  Amount=5000, EffectiveDate=2026-06-01, ExpiryDate=null

BillJob 处理6月后:
  新第一条:  (原记录到期)
    Amount=5000, EffectiveDate=2026-06-01, ExpiryDate=2026-06-30, IsActive=0
  新第二条:  (自动续期)
    Amount=5000, EffectiveDate=2026-07-01, ExpiryDate=null, IsActive=1
```

这样做的好处是：所有历史数据通过配置表的有效日期即可追溯，无需额外的时间轴表。

#### 4. 押金出账流程

##### 4.1 首次收取押金

第一次为合同生成账单时，若合同有押金且押金从未出过账，系统自动创建一条记费项：

```
触发时机: 首次生成该合同的账单时
动作:
  查询 DepositLogs 是否有 Action='Create' 的记录
  若该条押金从未被标记为"已出账":
    创建 ReceivablePlan (EntryType=Deposit, IsBilled=false)
    创建 Voucher + JournalEntry (借2241其他应付款-押金 / 贷1001银行存款)
  纳入当前账单一并出账
```

##### 4.2 押金变更

押金金额发生变化时，立即生成差异的记费项：

```
场景: 押金从1000 变更为 1200（增加200）
触发: 押金变更操作完成时
动作:
  计算差异额 = 新押金 - 旧押金 = 200
  立即创建 ReceivablePlan (EntryType=Deposit, Amount=200, IsBilled=false)
  立即创建 Voucher + JournalEntry

场景: 押金从1200 减少到 1000（减少200）
动作:
  创建 ReceivablePlan (EntryType=Deposit, Amount=-200, IsBilled=false)
  创建 Voucher + JournalEntry (红字冲销)
```

押金记费项在下次生成账单时自动纳入（IsBilled=false），无需手动干预。

#### 5. 补充收费项出账流程

##### 5.1 场景

合同中途新增收费项目（如签合同时未包含网费，后来补充收取），该收费项从某个历史日期开始生效。系统需要补收从生效日到当前月之前的所有月份的费用。

**核心流程：提交审批 → 审批通过 → 生成收费项和日记账 → 未出账收费项纳入账单**

##### 5.2 改造说明

补充收费当前直接写入 4 张主表（`ContractFeeConfigs` + `ReceivablePlans` + `Voucher` + `JournalEntry`），改造为审批驱动：

```
应收时间线 → [补充收费] 按钮（新增）
  → 选择费项、月度金额、生效日
  → 预览：展示各月分摊明细、会计凭证
  → 提交审批（CONTRACT_SUPPLEMENTARY_FEE）
  → 审批通过 → 写入 ContractFeeConfigs + ReceivablePlans + Voucher + JE
  → 审批驳回 → 暂存标记驳回，主表无数据
```

##### 5.3 约束规则
- 补充收费的生效日期 >= 合同起租日期
- 补充收费在审批通过后生成收费项和日记账
- 只补收当前月份之前（不含当月）的月份，当月费用由下次 BillJob 正常生成
- 已存在 (ContractId+FeeCodeId+Period) 的不重复生成
- 收费项是应收的记录（ReceivablePlan），日记账是会计分录（JournalEntry），层次不同

#### 6. 账单出账规则

| 场景 | 出账时机 | 包含内容 |
|------|---------|---------|
| 月度应收 | 每月25日 BillJob | 当月常规费用 + 所有未出账的补充收费/押金变更 |
| 手动出账 | 运营人员触发 | 指定合同下所有未出账记费项 |
| 补充收费 | 审批通过后生成记费项 | 补收月份的费用，等待下次出账 |
| 押金变更 | 变更时立即生成记费项 | 差额，等待下次出账 |

#### 7. 数据一致性要求

- **记费项幂等**：同一合同+同一费用项目+同一账期+同一条目类型 -> 不重复创建（已存在的 ReceivablePlan.ExistsByKey 检查已含 ContractId+FeeCodeId+Period）
- **出账幂等**：仅标记 IsBilled=false 的记录纳入账单，已出账不会重复出
- **费用配置自动续期幂等**：检查是否已有次月1日生效的同金额配置，若有则跳过


### 变更历史 — 需求

#### 1. 业务目标

## 六、调度任务并发约束

### 6.1 任务模板与实例

系统预定义五类任务模板，按公司维度独立创建实例：

| JobName | 显示名 | ScheduleType | 执行时间 | 分类 | TemplateCode |
|---------|-------|-------------|---------|------|-------------|
| BillJob | 月度应收生成 | Monthly | 每月25日 20:00 | 计费 | MonthlyFeeBill |
| SettleJob | 月度结算 | Monthly | 每月1日 22:00 | 计费 | LateFeeCalc |
| CollectionJob | 催缴任务 | Monthly | 每月15日 21:00 | 催缴 | Collection |
| AutoRenewJob | 自动续签 | Daily | 每天 00:00 | 合同 | AutoRenew |
| RenewalReminderJob | 续签提醒 | Daily | 每天 08:00 | 合同 | RenewalReminder |

每个公司从模板创建自己的任务实例，ScheduleType 支持 `Daily`（每天）和 `Monthly`（每月某日）两种类型。

### 6.2 执行隔离规则

| 场景 | 策略 |
|------|------|
| **不同公司 + 相同 Job** | ✅ 公司间并行（Parallel.ForEachAsync，默认并发度 = CPU 核数/2） |
| **相同公司 + 不同 Job** | ⚠️ 串行执行（按 TargetDate 升序逐个执行） |
| **相同公司 + 相同 Job** | ❌ 互斥（通过 TaskLogs.Status='Running' 检查 + 排期原子抢占双重防护） |

### 6.3 原子抢占机制

```
每 60 秒轮询：
  ① 查出所有 Pending 且 TargetDate≤现在 的排期
  ② 按 CompanyId 分组
  ③ Parallel.ForEachAsync 遍历各组（公司间并行）
      ④ 组内 foreach 逐个执行（公司内串行）
          ⑤ 原子 UPDATE SET Status='Processing' WHERE Id=@Id AND Status='Pending'
              ├─ 影响 0 行 → 已被其他周期抢占 → 跳过
              └─ 影响 1 行 → 抢占成功 → 继续执行
```

### 6.4 执行顺序依赖

```
同公司同一周期内按 TargetDate 升序执行（不可颠倒）：

  AutoRenewJob (每天 00:00) / RenewalReminderJob (每天 08:00)
       ↓ 新合同产生新应收
  BillJob (每月25日 20:00)
       ↓ 应收数据是滞纳金的基础
  SettleJob (每月1日 22:00，含滞纳金计算)
       ↓ 应收+滞纳金是催缴的依据
  CollectionJob (每月15日 21:00)
```

### 6.5 数据一致性要求

| 要求 | 说明 |
|------|------|
| **写-读一致** | BillJob 写入期间，CollectionJob 必须读到完整的应收数据（Snapshot 隔离） |
| **幂等性** | 重复执行不产生重复应收、重复滞纳金、重复催缴 |
| **事务完整性** | 每个 Job 在显式事务内执行，中途失败自动回滚 |
| **僵死检测** | Job 执行中崩溃，重启后能检测到未完成的任务（Heartbeat 30s，超时 5min 标记 Stale） |

### 6.6 并发防护级别

| 级别 | 措施 |
|:----:|------|
| 数据库约束 | 唯一索引防止重复 INSERT（应收、账单明细、执行锁） |
| 乐观锁 | RowVersion + 自动重试（CommitWithRetryAsync） |
| 业务逻辑 | 原子抢占（UPDATE ... WHERE Status='Pending'）+ 互斥检查 + TaskLogs 运行中检测 |




## 审批流 — 需求文档


## 1. 背景

现有审批流转模块（`ApprovalService.cs`）在线上持续出现 `DbUpdateConcurrencyException`，状态为"审批通过"时经常因乐观锁冲突导致操作失败。前后经过 4 次代码级别的修复尝试（RowVersion 重试、导航集合清理、Detach+重载、显式 RefreshConcurrencyAsync），均未能解决问题。

经深入排查，**根因不在 RowVersion 本身**，而在于 `MirrorAuditInterceptor` 在 `SavingChangesAsync` 阶段向不存在的 `_Audit` 审计表写入数据时，SQL Server 报错并破坏当前事务，后续的 UPDATE 在被终止的事务上执行 → 0 行影响 → `DbUpdateConcurrencyException`。

## 2. 问题根因

### 2.1 直接原因

```
SaveChangesAsync()
  → 注入审计字段 (UpdatedBy, UpdatedAt)
  → base.SaveChangesAsync()
    → 开启隐式事务
    → [Step 1] MirrorAuditInterceptor.SavingChangesAsync
        → ExecuteSqlRawAsync("INSERT INTO [ApprovalRequests_Audit] ...")
        → 表不存在 → SqlException 208, severity 16
        → SQL Server 终止事务
        → catch {} 静默吞掉异常                ← 掩盖根因
    → [Step 2] DomainEventDispatcher.SavingChangesAsync
    → [Step 3] EF Core 执行 UPDATE 于已终止事务
        → 0 行受影响 → DbUpdateConcurrencyException ← 表象
    → [Step 4] DomainEventDispatcher.SavedChangesAsync (永远走不到)
```

### 2.2 深层原因

| 问题 | 说明 | 影响范围 |
|------|------|---------|
| 审计表缺失 | `ApprovalRequests_Audit`、`Contracts_Audit` 等 19 张 `{Table}_Audit` 表在数据库中不存在 | **全部**修改 `AuditableEntity` 的操作 |
| `catch {}` 静默吞异常 | `MirrorAuditInterceptor` 的空 catch 块掩盖了 SQL 错误 | 错误无法被发现和定位 |
| RowVersion 双重并发 | `Status` 和 `RowVersion` 同时作为并发令牌，后者在审计写入失败时被错误归咎 | 干扰排查方向 |
| 重试逻辑无法恢复 | 每次重试都走同样被破坏的管道，审计写入每次都失败 | 所有重试全部无效 |

## 3. 需求

### 3.1 功能需求

| # | 需求 | 优先级 |
|---|------|--------|
| R1 | 审批通过（Approve）操作必须稳定可靠，不因后台审计写入失败而阻塞 | P0 |
| R2 | 审批驳回（Reject）操作同 R1 | P0 |
| R3 | 审计表缺失不应影响正常业务操作 | P0 |
| R4 | 仍保留乐观锁保护，防止重复审批 | P0 |
| R5 | 审计写入失败的场景应有日志记录，不可静默掩盖 | P1 |

### 3.2 非功能需求

| # | 需求 | 指标 |
|---|------|------|
| NR1 | 审批操作 99.9% 场景下一次 Commit 成功 | ≥99.9% 首次通过 |
| NR2 | 审计写入失败不影响主事务 | 零影响 |
| NR3 | 代码可维护性 | 重试逻辑不超过 2 层嵌套 |

### 3.3 不在此次范围

- 审批流程本身的业务规则变更（审批级别、流转逻辑等）
- 前端 UI 改动
- 现有 `AuditService.GetStatsAsync` 改造
- 领域事件 Outbox 模式

## 通用批量导入 — 需求文档


## 1. 背景

系统有多处需要批量导入数据且经审批后才能生效：房源导入、合同导入、租客导入等。需要一个**通用导入审批框架**，统一处理公共流程，同时允许各场景差异化的校验和执行逻辑。

## 2. 设计原则

- **数据库不允许存 JSON 原始数据** — 所有字段必须有明确定义的列和类型
- **通用与独立分离** — 各导入类型共用的字段放入基础表，差异字段放入类型专属扩展表
- **审批驱动** — 所有导入均需审批通过后才创建业务数据
- **重导兼容** — 同一份文件可修正后重新导入，已创建的行自动跳过

## 3. 适用范围

| 导入类型 | 代码标识 | 关联审批类型 | 优先级 |
|----------|----------|-------------|--------|
| 房源导入 | `HousingUnit` | 批量导入房屋（三级审批） | **P0 当前实现** |
| 合同导入 | `Contract` | 新建合同（三级审批） | P1 后续 |
| 租客导入 | `Tenant` | 待定 | P2 后续 |

## 4. 通用流程

```
① 下载模板 → ② 填写数据 → ③ 上传 Excel → ④ 系统校验
  → ⑤ 有效行暂存 → ⑥ 提交审批 → ⑦ 审批通过 → ⑧ 创建业务实体
```

- 步骤 ④⑤⑥ 为**同步**（用户等待结果）
- 步骤 ⑦⑧ 为**异步**（审批人操作后自动执行）

## 合同续签 — 需求文档


### 1. 背景

合同到期后续租是租赁业务的常见场景。当前系统存在以下问题：

- 续签不走审批流，直接 SQL 操作，存在运营风险
- 无欠费检查，欠租也能续签
- 无押金处理策略（原押金延续 / 重新收取）
- 无市场参考价展示
- 续签合同编号与原合同无关联
- 续签期间无并发控制，可同时提交多个冲突的变更

### 2. 核心业务规则

| 规则 | 说明 |
|------|------|
| **新建合同 + 强关联** | 续签采用"新建合同 + PreviousContractId 强关联"，保留原合同完整历史 |
| **未到期续签原合同保持 Active** | 原合同仍在有效期内的，续签后保持 Active 状态，继续正常生应收到租期结束；新合同从原合同到期日次日起租，无缝衔接 |
| **已到期续签原合同设为 Renewed** | 原合同已到期的，续签后设为 Renewed 终态 |
| **新合同自由** | 新合同是完全独立的 Active 合同，所有操作可修改 |
| **欠费拦截** | 有未结清应收时强制拦截续签，不允许提交 |
| **重复续签拦截** | 已有一份合同的 PreviousContractId 指向本合同，则不允许再次续签 |
| **统一并发锁** | 同一合同同时只能有一条待审批流（续签/调租/终止互斥） |

### 3. 续签流程

#### 阶段 1：续签预览
- 用户点击续签 → 系统检查欠费状态、是否有冲突的待审批流、**是否已被续签**
- 展示同户型市场参考价、继承的费用配置和租客列表
- 用户填写新月租、新到期日、押金策略

#### 阶段 2：审批提交
- 数据写入 `RenewalRequests` 表（不触碰主表）
- 创建 `ApprovalRequest`（类型：CONTRACT_RENEW）
- 根据新月租金额自动路由审批级别

#### 阶段 3：审批执行
- **审批通过 → 事务中执行：**
  - 原合同 **已到期（Expired）** → 标记为 `Renewed`（终态）
  - 原合同 **未到期（Active）** → **保持 Active**，继续正常生应收
  - 创建新合同（起租日 = 原合同到期日 + 1）
  - **复制费用配置 → 再过期原合同费用配置**（★ 顺序重要：必须先查询复制，再将原配置设为到期，否则复制时会查不到数据）
  - 复制租客，处理押金，生成首期应收
- 审批驳回 → `RenewalRequests.Status=Rejected`，主表无变动

### 4. 并发控制要求

同一合同在任意时刻只能有一个待审批的变更请求：

```sql
-- 统一检查：
SELECT 1 FROM ApprovalRequests 
WHERE ContractId = @ContractId AND Status = 'Pending'
```

| 已有待审批流 | 能否提交续签 | 能否提交调租 | 能否提交终止 | 能否提交费用调价 |
|:-----------|:----------:|:----------:|:----------:|:--------------:|
| 任何类型 | ❌ | ❌ | ❌ | ❌ |

### 5. 押金处理

| 策略 | 说明 |
|------|------|
| **TRANSFER**（原押金延续） | 原押金转移到新合同，无资金变动，DepositLog 记录转移 |
| **NEW**（重新收取） | 增大：原押金退还 + 新押金全收，差额生成应收计划 |
| | 减少：差额退还租客，新合同记新押金 |

### 5.1 押金数据一致性要求

续签提交时，`RenewalRequest` 实体中的 `NewDepositAmount`（新押金金额）通过 `DapperRepository<T>.AddAsync` 自动生成 INSERT 语句写入数据库。该自动机制要求：

| 要求 | 说明 |
|------|------|
| **可空值类型必须参与 INSERT** | 实体中的 `decimal?`、`Guid?`、`DateTime?` 等可空值类型属性不能因类型检查被排除在自动生成 SQL 之外 |
| **INSERT 列完整性** | 所有非导航属性（含可空值类型）必须纳入 INSERT 列列表，确保字段值被持久化 |
| **读取回填正确** | 从数据库加载的实体必须能还原所有已提交字段，不得因写入缺失导致回退到默认值 |

反例：若 `NewDepositAmount`（`decimal?`）因可空值类型在自动生成 INSERT 时被排除，则写入后该字段在数据库中为 NULL。续签执行时 `ExecuteRenewalAsync` 加载的实体的 `NewDepositAmount = null` → `renewal.NewDepositAmount ?? renewal.OldDepositAmount` 回退到旧押金 → 新合同押金错误。

### 5.2 审批描述与数据一致性校验

审批描述中展示的押金信息（`押金：¥10,000.00 → ¥10,020.00（重新收取）`）源于提交时的请求参数，仅用于审批人查看。系统必须以 `RenewalRequest` 表中持久化的 `NewDepositAmount` 作为续签执行时的唯一数据源。审批描述与持久化数据应保持一致，如有差异说明存在数据写入缺陷。

### 6. 合同编号规则

编号基于**原始合同号 + 续签次数**，每次续签剥离已有 `-R{n}` 后缀后重新拼接：

```
原合同:       HT-2026-001       (RenewalCount=0)
第1次续签:    HT-2026-001-R1    (RenewalCount=1)
第2次续签:    HT-2026-001-R2    (RenewalCount=2)
第n次续签:    HT-2026-001-R{n}  (RenewalCount=n)
```

实现逻辑：
```csharp
var baseNo = oldContract.ContractNo.Split("-R").First();  // 剥离后缀
var newContractNo = $"{baseNo}-R{oldContract.RenewalCount + 1}";
```

### 7. 重复续签拦截

已续签的合同不可再次提交续签。判断标准为：

```sql
-- 如果存在另一份合同的 PreviousContractId 指向本合同，说明已被续签
SELECT 1 FROM Contracts WHERE PreviousContractId = @thisContractId
```

| 拦截点 | 表现 |
|--------|------|
| **列表页/详情页** | 续签按钮直接隐藏（`!hasRenewalContract` 条件渲染） |
| 预览 API | `concurrentApprovals.alreadyRenewed = true` + 阻塞提示 |
| 提交 API | 400 拒绝："该合同已被续签（新合同号：XXX），不可再次续签" |

### 8. 已续签判断标准

判断一份合同是否已被续签，不再依赖 `StatusCode = 'Renewed'`，而是通过链路字段：

| 方式 | 可靠性 | 适用范围 |
|------|:------:|---------|
| `PreviousContractId = 本合同Id` 存在记录 | ✅ 不可篡改 | 所有场景（Active/Expired 续签都适用） |
| `StatusCode = 'Renewed'` | ❌ 仅已到期场景 | 仅 Expired 续签后可用 |

未到期合同续签后，原合同保持 Active 状态，但可以通过 `SELECT 1 FROM Contracts WHERE PreviousContractId = 原合同Id` 判断其已被续签。

### 7. 待审批表命名规范

所有"待审批数据"统一以 `Request` 后缀标识：

| 表名 | 说明 |
|------|------|
| `RenewalRequests` | 续签待审批数据 |
| `ChangeRequests` | 合同变更待审批数据 |
| `ChangeRequestItems` | 变更明细（字段级） |
| `ApprovalRequests` | 通用审批流（已有） |


## 自动续签 — 需求文档


### 1. 背景

合同到期后续签是高频场景。目前设计为审批驱动的续签流程（CONTRACT_RENEW），但需要运营人员手动提交。为进一步减少人工操作，引入自动续签机制：**系统提前 7 天自动发起续签审批，运营人员通过看板批量管理续签任务。**

### 2. 核心原则

| 原则 | 说明 |
|------|------|
| **审批驱动不变** | 自动续签只是自动"提交"审批，不跳过审批流程 |
| **提前 7 天发起** | 到期日 T-7 天 05:00 提交续签审批，预留审批缓冲期 |
| **管理员可干预** | T-14 天起通知管理员，可调整参数、提前提交或关闭 |
| **参数可配置** | 续签租金规则、租期规则、欠费策略由系统配置控制 |

### 3. 自动续签 Job

#### 3.1 AutoRenewJob

| 属性 | 值 |
|------|-----|
| 触发时间 | 每天 05:00 |
| 筛选条件 | `EndDate = 今天 + 7 天` AND `Status = Active` AND `AutoRenew = true` AND 无已提交审批 |
| 操作 | 调用 `RenewalService.SubmitAsync`（系统账户） |
| 欠费处理 | 有欠费则跳过，记录日志 |

#### 3.2 RenewalReminderJob

| 属性 | 值 |
|------|-----|
| 触发时间 | 每天 08:00 |
| 筛选条件 | `EndDate = 今天 + 14 天` AND `Status = Active` AND `AutoRenew = true` |
| 操作 | 按天聚合发送站内通知给运营主管角色 |

### 4. 通知设计

#### 4.1 聚合通知

按日期聚合，同一管理员同一天只收到一条通知：

```
🔔 合同续签提醒
本月有 8 份合同即将到期（自动续签）
- 本周到期：5 份
- 下周到期：3 份
- 其中 2 份有欠费记录
[查看待续签看板]
```

#### 4.2 接收人

| 角色 | 原因 |
|------|------|
| **运营主管（OpsSupervisor）** | CONTRACT_RENEW 第 1 级审批人，需提前知晓 |
| **部门经理（DeptManager）** | 金额较大时涉及 2 级审批 |
| **系统管理员** | 兜底通知 |

### 5. 待续签看板

独立页面，聚合展示所有即将到期的合同，支持批量操作：

| 功能 | 说明 |
|------|------|
| 统计概览 | 即将到期/自动续签/手动处理/已关闭 数量 |
| 合同列表 | 按到期日排序，每行显示合同号/房源/租客/到期日/月租 |
| 批量操作 | 多选 → 批量调整租金/批量调整租期/批量关闭自动续签/全部提交 |
| 逐项操作 | 展开 → 调整单条续签参数（租金/租期/押金） |
| 状态标记 | Pending / ParamsAdjusted / ApprovalSubmitted / AutoRenewDisabled / AutoProcessed / Skipped |

### 6. 管理员操作路径

```
收到通知 → 查看看板
  │
  ├─ 调整参数 → 保存 → T-7 天 AutoRenewJob 按新参数提交
  ├─ 立即提交 → 手动提交续签审批 → 标记已处理
  ├─ 关闭续签 → AutoRenew = false → 到期后变为 Expired
  └─ 不处理   → T-7 天 AutoRenewJob 按默认参数自动提交
```

### 7. 新合同起租日规则

固定为 `旧合同.EndDate + 1`，无论审批何时通过：

| 审批通过时间 | 起租日 | 说明 |
|------------|--------|------|
| 到期日前通过 | 旧.EndDate + 1 | 新合同待命 |
| 到期日当天通过 | 旧.EndDate + 1 | 同日生效 |
| 到期日后通过 | 旧.EndDate + 1 | 起租日回溯，无缝衔接 |

### 8. 新增数据字段

| 表 | 字段 | 说明 |
|----|------|------|
| `Contracts` | `AutoRenew BIT DEFAULT 1` | 是否自动续签 |
| `Notifications` | — | 新表，站内通知存储 |
| `AutoRenewConfig` | — | 新表，续签策略配置 |

### 9. 配置项

| 配置 | 默认值 | 说明 |
|------|--------|------|
| `AdvanceDays` | 7 | 提前几天提交续签 |
| `RentRule` | Same | 续签租金规则（Same / Percentage / MarketPrice） |
| `RentIncreasePercent` | null | 涨幅百分比 |
| `TermRule` | Same | 续签租期规则（Same / FixedMonths） |
| `TermMonths` | 12 | 固定月数 |
| `OverdueAction` | Block | 欠费处理方式（Block / WarnAndContinue / Skip） |

### 2. 通知分类

- **Pinia Store**：新建 `notification` store，管理通知列表、未读计数、loading 状态，提供 `startPolling()` / `stopPolling()` 生命周期方法

### 7. 开发规范：SQL 集中管理

所有 Dapper SQL 查询语句统一存放在 `SqlMaps.xml` 单一文件中，禁止在 Controller、Service、Repository 中以字符串形式散落内联 SQL。

| 规则 | 说明 |
|------|------|
| **存放位置** | 唯一来源 `SqlMaps.xml`，应用启动时一次性加载到内存 |
| **命名格式** | `{模块}.{CRUD}.{实体}.{描述}`（如 `Approval.Select.Request.PendingByUser`） |
| **CRUD 动词** | 固定四种：`Select` / `Insert` / `Update` / `Delete` |
| **启动校验** | 所有 SQL 在应用启动时完成加载，id 重复或 XML 格式错误立即抛出异常 |
| **运行时** | 仅限 `SqlLoader.Get(id)` O(1) 字典查找，不允许拼接 SQL |
| **例外** | 泛型 `DapperRepository<T>` 的反射动态 SQL 不受此限，但需注意其 `IsNavProp` 过滤逻辑：必须正确识别 `Nullable<T>`（可空值类型）不是导航属性，避免将其排除在自动生成的 INSERT/UPDATE 列列表外 |

### 8. 数据库设计规范

系统不使用数据库外键约束，表间关联通过代码逻辑维护。

| 规则 | 说明 |
|------|------|
| **禁止外键** | `CREATE TABLE` 中不允许出现 `FOREIGN KEY` 或 `REFERENCES` 子句 |
| **关联列保留** | 外键列正常定义（如 `UserId` GUID NOT NULL），仅去掉约束 |
| **一致性保障** | 由应用层 Service + Repository 保证，不依赖数据库层 |
| **建表检查** | 新增表时审查是否含有 FK 定义，如有则去掉 |

## 九、合同续签费用配置日期规则

### 1. 业务背景

合同续签后，原合同的费用配置仍在系统中标记为"生效中"（ExpiryDate=NULL），新合同复制的费用配置生效日期为空，导致费用配置的时间轴数据不准确，影响后续按时间段的费用核算。

### 2. 需求描述

#### 2.1 续签执行时的日期处理

续签审批通过并执行时，系统应自动处理原合同和新合同的费用配置日期：

| 实体 | 生效日期 | 到期日期 | 状态 |
|---|---|---|---|
| **原合同费用配置** | 保持原值 | **原合同到期日** | IsActive=0（已到期） |
| **新合同费用配置** | **新合同起租日** | NULL | IsActive=1（生效中） |

#### 2.2 规则定义

| 规则 | 说明 |
|---|---|
| **原合同费用到期日** | 续签执行时，原合同所有 ExpiryDate=NULL 的费用配置 → ExpiryDate=原合同到期日, IsActive=0 |
| **新合同费用生效日** | 续签复制费用配置时，EffectiveDate=新合同起租日（原合同到期日+1天） |
| **用户不可修改** | 上述日期由系统自动计算，用户无需干预 |

### 3. 影响范围

| 模块 | 影响 |
|---|---|
| `RenewalService.ExecuteRenewalAsync` | 续签执行时更新原合同费用配置到期日 + 新配置生效日 |
| 前端合同详情页 | 无改动（已有 ExpiryDate 显示逻辑） |

## 十、审批业务数据展示

### 1. 业务背景

审批人在审批时，只能看到审批标题和描述文本，无法直观对比业务数据的变化（如租金调整前后的金额、续签前后的租期等），影响审批效率。

### 2. 需求描述

#### 2.1 统一业务详情展示

审批详情页新增"业务数据"Tab，以对比表形式展示审批关联的业务数据变化：

## 十一、合同操作闭环方案（调价/终止/暂停）

### 1. 背景

三大合同操作（费用调价、合同终止、暂停/恢复）当前存在以下问题：

| 问题 | 说明 |
|---|---|
| **路径分裂** | 调价有三条并行路径（直接调价绕过审批/审批弹窗无回调落盘/变更请求），行为不一致 |
| **状态机破坏** | 终止操作先 `Terminate()` 再覆写状态绕过状态机，且 `PendingApproval→Terminated` 转换不存在，**审批通过后回调必然报错** |
| **应收不联动** | 终止后未取消未结清应收计划；暂停期间已生成的应收不冻结；调价后费用版本化不参与应收计算 |
| **审批数据非结构化** | 生效日期、金额等关键参数嵌入 Description 文本，正则解析不可靠 |
| **并发无守卫** | 调价/终止/续签可同时提交，缺少统一的 pending 审批拦截 |

### 2. 总流程规范

```
【审批前】
  并发守卫: EnsureNoPendingForContract(contractId)
  └─ 同一合同同一时间只能有一条待审批流（调价/终止/续签互斥）

【审批提交】
  ┌─ 写 ApprovalBizData 表（结构化业务数据）
  ├─ 写 ApprovalFeeItems 表（调价时，逐条费用项）
  └─ 写 ApprovalRequest（TargetEntityType 细化区分操作类型）
  ※ 以上三步在显式事务中完成

【审批回调】
  ┌─ 幂等检查（IsProcessed）
  ├─ 执行业务操作（调费用配置/终止合同）
  ├─ 联动应收（重算/取消/冻结）
  ├─ 标记 IsProcessed
  └─ 通知相关人
```

### 3. 费用调价（调价）

| 要素 | 说明 |
|---|---|
| **路径统一** | 取消直接调价路径（`ContractFeeConfigsController.Adjust`），仅保留审批路径 |
| **审批类型** | `CONTRACT_FEE_CHANGE`（Fixed，固定1级运营主管） |
| **入库逻辑** | `ApprovalBizData.ChangeType = 'FEE_ADJUST'` + `ApprovalFeeItems` 逐条存每个费用项的原价/新价/计费模式 |
| **审批通过回调** | 遍历 `ApprovalFeeItems`，对每条调用 `AdjustFeeConfig`（FixedAmount 调 Amount，MeterBased 调 UnitPrice） |
| **应收联动** | 从生效日期起按新费率计算，`ContractFeeConfig.EffectiveDate/ExpiryDate` 参与账期过滤 |
| **驳回处理** | 费用配置无变化 |

### 5. 合同终止

| 要素 | 说明 |
|---|---|
| **关键修复** | Controller 不再提前调 `contract.Terminate()`，改为审批通过后执行 |
| **审批类型** | `CONTRACT_TERMINATE`（AmountBased，押金金额路由：≤5000→1级，5000~50000→2级，50000+→3级） |
| **入库逻辑** | `ApprovalBizData.ChangeType = 'TERMINATE'`，存 TerminateType/ActualEndDate/DepositReturn/Reason |
| **审批通过回调** | `ExecuteContractTermination()` 一次性完成：①Terminate ②取消未结清应收 ③费用配置到期 ④押金处理 |
| **0 级审批** | 无审批配置时直接同步执行 `ExecuteContractTermination()`，与列表页/详情页行为统一 |
| **应收联动** | 未结清应收（Pending/Partial/Overdue）→ Cancelled；有部分收款的记录待退款 |

### 6. 暂停 / 恢复

| 要素 | 说明 |
|---|---|
| **暂停审批** | 0 级（直接执行，无需审批） |
| **入库逻辑** | `ApprovalBizData.ChangeType = 'SUSPEND'`，记 Reason（用于历史追溯） |
| **暂停操作** | `contract.Suspend()` → 冻结未来应收（Pending→Frozen）→ 触发 `ContractSuspendedEvent` |
| **恢复操作** | `contract.Resume()` → 解冻应收（Frozen→Pending）→ 补充生成应收（分批，每批最多6个月）→ 触发 `ContractResumedEvent` |
| **暂停期间** | 已有 `ShouldGenerateReceivableFor()` 返回 false + `GenerateAsync()` 拦截，不生成新应收 |
| **领域事件修复** | `Resume()` 补充写入 `ResumedAt` |

### 7. 并发控制

| 规则 | 说明 |
|---|---|
| **统一守卫** | `SELECT COUNT(1) FROM ApprovalRequests WHERE ContractId=@Id AND Status='Pending'` |
| **互斥范围** | 调价/终止/续签互斥，一次只能有一个待审批流 |
| **守卫复用** | 提升 `RenewalService.EnsureNoPendingApprovalAsync()` 为公共方法 |
| **ContractId 赋值** | 所有新增端点提交审批时回写 `ApprovalRequest.ContractId` |

### 8. 数据存储规范

| 规则 | 说明 |
|---|---|
| **结构化表** | 所有业务数据存入 `ApprovalBizData` + `ApprovalFeeItems`，不存 JSON |
| **TargetEntityId** | 保持指向 `Contract.Id`（不变），不影响现有并发守卫和审批路由 |
| **幂等设计** | `ApprovalBizData.IsProcessed` 标记回调执行状态，失败可重试 |
| **事务性** | BizData 写入 + 审批提交在同一显式事务中 |

## 十二、账单-会计闭环方案

### 1. 总设计原则

```
权责发生制：出账即确认收入，收款即确认现金
Journal 不可变：出账记录写入后永不更改，错误通过负数冲销修正
BillJob 自动过账：BillJob 出账时同步生成 GL 分录（GLPosted=1）
手动创建需过账：非 BillJob 创建的 Journal 需在日记账页手动过账
去累计快照：余额由 GeneralLedgerEntries 逐笔分录实时汇总
DebitNote 含预付：账单显示总额、预付抵扣、应付余额
利息可豁免：利息 Journal 不过 GL（GLPosted=0），豁免时直接取消
```

### 2. 核心数据结构

| 表 | 角色 | 说明 |
|---|------|------|
| `Journal` | **日记账** | 出账流水，记录每个合同的应收费用。GLPosted 标记是否已过账 |
| `GeneralLedgerEntries` | **总账分录** | 逐笔科目级借贷变动，按期间+科目可汇总余额 |
| `Receipt` | **收款单** | 客户付款记录 |
| `DebitNote` | **账单** | 出账时给租客的对账凭证，含预付抵扣 |

### 3. 会计科目表

| 编码 | 科目名称 | 类型 | 方向 | 用途 |
|------|---------|------|------|------|
| 1002 | 银行存款 | 资产 | 借增贷减 | 收款入账 |
| 1122 | 应收账款 | 资产 | 借增贷减 | 出账应收、利息 |
| 2203 | 预收账款 | 负债 | 贷增借减 | 超额收款、预收抵应收 |
| 2241 | 其他应付款-押金 | 负债 | 贷增借减 | 租客押金 |
| 6001 | 主营业务收入 | 收入 | 贷增借减 | 出账收入 |

### 4. 分录规则

| 事件 | GL 分录 |
|------|---------|
| BillJob 出账 | Debit 1122 / Credit 6001 |
| 手动过账 | Debit 1122 / Credit 6001 |
| 收款确认 | Debit 1002 / Credit 1122（offset）/ Credit 2203（overflow） |
| 预收抵应收 | Debit 2203 / Credit 1122（不生成 Journal） |
| 利息 | Journal(GLPosted=0)，不进 GL |

### 5. BillJob 完整流程

```
对每个合同：
  ├─ 生成当期 Journal(GLPosted=1) + 写 GL
  ├─ 拾取未入账单（DebitNoteId IS NULL）
  │    GLPosted=0 → 自动过账 + 写 GL
  │    GLPosted=1 → 跳过
  ├─ 查询合同 PrepaidBalance
  ├─ 创建 DebitNote（含预付抵扣）
  └─ 回写 DebitNoteId
```

### 6. 日记账过账

```
勾选 GLPosted=0 的行 → 点击过账
  → UPDATE GLPosted=1
  → 写 GL（Debit 1122 / Credit 6001）
```

### 7. 调度任务

| 任务 | 时间 | 说明 |
|------|------|------|
| BillJob | 每月25日20:00 | 出账：Journal(GLPosted=1) + 写 GL + DebitNote |
| SettleJob | 每月1日21:00 | 预收抵应收（写GL）+ 利息（GLPosted=0） |

## 十三、任务调度框架

### 1. 调度三件套

| 组件 | 职责 | 频率 |
|---|---|---|
| **JobSchedule**（任务定义） | 定义任务 + 调度类型（Daily/Monthly）+ 时分参数（全局模板 + 公司自定义） | 持久配置 |
| **JobScheduleGenerator**（调度生成器 ★） | 读取 JobSchedule → 按 ScheduleType/Hour/Minute/DayOfMonth 计算下个执行时间 → 生成 JobScheduleExecution | 每小时 |
| **SchedulingHostedService**（调度执行器） | 轮询 Pending Execution（TargetDate≤Now）→ 原子抢占 → 分组并行执行 | 每 60 秒 |

### 2. 并发模型

#### 2.1 两级并发控制

```
Parallel.ForEachAsync(公司分组)          ← 公司间并行
  │  foreach(组内排期, OrderBy TargetDate)  ← 公司内串行
  │    ├─ 原子抢占（UPDATE ... WHERE Status='Pending'）
  │    ├─ 互斥检查（TaskLogs 运行中检测）
  │    ├─ 创建 TaskLog + TaskStepLog
  │    ├─ 执行 job.ExecuteAsync()
  │    └─ 更新 Execution + TaskLog 状态
```

| 参数 | 默认值 | 说明 |
|---|---|---|
| 公司级并行度 | `Max(1, CPU/2)` | Parallel.ForEachAsync 自动调度 |
| 合同级并行度 | **20** | 单 Job 内部（BillJob/SettleJob）合同并行数 |
| 原子抢占 | `UPDATE ... AND Status='Pending'` | 防止多周期重复执行 |

#### 2.2 原子抢占流程

```
① SELECT 到期排期       → 查出所有 Pending 且 TargetDate≤Now
② 预处理 JobSchedule    → 预加载关联的活跃 JobSchedule，过滤无效项
③ 按 CompanyId 分组    → 多公司并行执行
④ 原子抢占              → UPDATE Status='Processing' WHERE Id=@Id AND Status='Pending'
⑤ 抢占成功则继续       → 否则跳过（已被其他周期处理）
⑥ 执行 → 标记完成/失败
```

### 3. 步骤级执行日志

所有任务按步骤记录耗时和影响数：
- **TaskLogs** — 任务级（执行状态/总耗时/成功数/失败数）
- **TaskStepLogs** — 步骤级（每步耗时/影响数/错误信息）
  - 宿主层步骤：`Schedule.Execute`（调度引擎自动记录）
  - 业务层步骤：`BillStep01~04`、`SettleStep01~04`（Job 内部记录）

### 4. 新公司自动注册

新建公司时系统自动完成：
```
公司创建 → CompanyCreatedEvent → 从全局模板复制 JobSchedule
→ Generator 生成 Execution → 到点自动执行
全程无需人工干预
```

### 5. 任务执行模式

所有定时任务支持三种执行模式：

| 模式 | 英文 | 触发方式 | 是否写数据 | 通知 | 使用场景 |
|---|---|---|---|---|---|
| **自动** | Scheduled | 定时器触发 | ✅ 写入 | ✅ 发送 | 每月25日/1日定时执行 |
| **手动** | Manual | 管理员 API | ✅ 写入 | ❌ 不发送 | 提前出账、失败重跑、指定合同 |
| **预执行** | DryRun | 管理员 API | ❌ 只查不写 | ❌ 不发送 | 预检数据完整性、预览预估 |

**时间安排**：手动和预执行的**执行时间**为 API 调用时的系统时间，**目标账期**由请求参数 `targetMonth` 指定（如 `"2026-08"` 处理 8 月数据）。

**DryRun（预执行）返回内容**：
- 预估合同数 / FeeConfig 数 / 应收条数 / 账单数
- 预估总金额
- 警告列表（科目模板缺失、预收不足等）

**手动执行支持参数**：
- `contractIds` — 只处理指定合同（失败重跑时使用）
- `force` — 强制跳过执行锁（修复卡住的任务）

**自动执行记录**：TriggerType=Scheduled，独立于手动记录。
**手动执行记录**：TriggerType=Manual，支持指定合同范围和强制模式。

### 6. 中断检测与恢复

#### 6.1 心跳检测

TaskLogs 每 30 秒更新 HeartbeatAt，超时 5 分钟自动标记为 Stale（僵死）。

#### 6.2 恢复机制

进程崩溃后，重启时自动检测 Stale 任务：

```
检测到 TaskLog(Status=Running, HeartbeatAt>5min) → 标记 Stale
StepLog 中记录了哪些合同已完成（逐合同 StepLog 与事务绑定）
重跑时：已完成的合同幂等跳过，未完成的合同正常生成
```

#### 6.3 反转

任务误执行后可通过 Reverse API 取消：
- 安全检查（该期是否有收款 → 禁止反转）
- 通过后删除本次任务产生的所有数据（ReceivablePlan + JE + DebitNote）

### 7. 通知

| 触发 | 通知谁 | 内容 |
|---|---|---|
| BillJob 成功 | 运营 | 汇总数据（45合同/128万/45账单/12s） |
| BillJob 失败 | 运维 | 失败步骤/合同/原因/修复建议 |
| SettleJob | 运营 | 预收不足合同列表 |
| TerminateJob | 租户 | 终止结算单已生成 |

### 8. 生成默认排期规则

#### 规则一：可执行判断

```
Monthly 任务（如 BillJob 每月25日 20:00）:
  当月执行时间 = DateTime(今年, 当月, Min(25,当月天数), 20, 0, 0)
  当前时间 ≤ 当月执行时间 → 从当月开始生成
  当前时间 > 当月执行时间 → 从下月开始生成

Daily 任务（如 AutoRenewJob 每日 05:00）:
  当天执行时间 = DateTime(今年, 当月, 当天, 5, 0, 0)
  当前时间 ≤ 当天执行时间 → 从今天开始生成
  当前时间 > 当天执行时间 → 从明天开始生成
```

#### 规则二：年份覆盖

```
开始月 ≤ 11月（1~11月）:
  → 仅当年: 开始月/日 → 当年12月31日
  示例: 7月生成 → 7月~12月; 11月生成 → 11月~12月

开始月 > 11月（12月）:
  → 当年 + 次年: 开始月/日 → 当年12月31日 + 次年1月1日~12月31日
  示例: 12月生成 → 12月 + 次年1月~12月
```

#### 规则三：幂等

同任务同月份（Daily 为同日期）已存在 → 跳过，不重复创建。

#### 节假日调整

BillJob 每月 25 日如果遇到周末或法定节假日，自动调整到最近的工作日：

- 查 `HolidayCalendars` 表获取当年+次年节假日数据（含调休上班标记）
- 周六日 + 非调休上班 → 非工作日 → 调整
- 周六日 + 调休上班（`IsWorkingDay=true`）→ 工作日 → 不调整
- 调整规则：向前/向后找距离最近的工作日（距离相等时取后面的）
- 调整结果记录在排期：`TargetDate`=调整后日期、`OriginalDate`=原日期、`IsAdjusted=true`、`Reason` 记录原因

**示例**：
```
原计划: 2026-07-25（周六）
  → 向前: 07-24(周五) ✅ 距离1天
  → 向后: 07-26(周日)❌ 07-27(周一) ✅ 距离2天
  → 最近: 07-24(周五) ✅ 往前调整1天
  → 排期: TargetDate=07-24, OriginalDate=07-25, Reason="2026-07-25逢周末/节假日，调整至2026-07-24"

原计划: 2026-09-26（周六，调休上班）
  → HolidayCalendars.IsWorkingDay=true → 工作日 → 不调整 ✅
```

#### 示例

```
场景 1: 当前 2026-07-15（7月≤10, 从当月开始）
  → 生成: 2026-07~2026-12（共 6 条，Annual 任务为 ~168 条）

场景 2: 当前 2026-07-28（7月≤10, 当月已过, 从下月开始）
  → 生成: 2026-08~2026-12（共 5 条）

场景 3: 当前 2026-11-15（11月≤11, 仅当年）
  → 生成: 2026-11~2026-12（共 2 条）

场景 4: 当前 2026-12-15（12月>11, 从当月开始）
  → 生成: 2026-12 + 2027-01~2027-12（共 13 条）
```

### 2. 权限控制模型

```

#### 3. 日记账（JournalEntry）生成核心规则

##### 3.1 时间边界

费用变更发生在 BillJob 执行时间（例：每月24日20:00）的前后，结果不同：

- **BillJob 执行前 FeeConfig 变更已提交** → BillJob 读到新金额 → JE 正确，不需补差
- **BillJob 执行后 FeeConfig 才提交** → 8月账单已出 → 需生成 Supplementary 补差 JE

##### 3.2 两种生成方式

| 方式 | 触发 | 处理范围 | 用途 |
|------|------|---------|------|
| Supplementary（事件驱动） | 费用调价/漏配审批通过 | 已出账单的月份 | 差价补足 |
| BillJob（定时生成） | 每月定时任务 | 下一个月 | 正常计费 |

OneTime 例外：押金等一次性费用不受 BillJob 时间边界影响，合同签署时立即生成 Immediate JE。

##### 3.3 补差条件

判断标准：生效月 M 的 JE 是否已出账单（已出 = M ≤ 当前月+1）

| 条件 | 处理 |
|------|------|
| 已出账单（M ≤ 当前月+1） | 生成 Supplementary 补差 JE，在下次 BillJob 汇总 |
| 未出账单（M > 当前月+1） | 不做处理，BillJob 后续执行时自动用新金额 |

##### 3.4 补差计算

| 生效月位置 | 计算方式 |
|-----------|---------|
| M < 当前月（过去月） | 整月全额差价 |
| M = 当前月（本月） | 分摊计算（生效日~月底按天比例） |
| M = 当前月+1（下月，已出账单） | 整月全额差价 |
| M > 当前月+1（未出账单） | 不生成补差 |

##### 3.5 费用调价后的 JE 联动处理

```
FeeConfig 变更 → 过期旧配置 → 创建新配置
  → 判断生效月 M 是否已出账单？
    YES → 计算差价 → 生成 Supplementary Voucher + JE
       → DEBIT 1122 / CREDIT 6001(或6051) = 差价
    NO → 不做处理
  → Commit
```

#### 4. BillJob 改造

BillJob 每月执行一次，生成**下一个月**的 JE：

```
Step 1：生成下一个月 JE（正常计费）
  → 查询 Recurring FeeConfigs → 分摊计算 → 去重检查 → 插入 Voucher
Step 2：汇总未结清 Supplementary JE
  → 查找 SourceEntityType='ContractFee.Supplementary' 的未结算 JE
Step 3：生成 ReceivablePlan + DebitNote
  → 汇总 Step1 + Step2 → 生成应收 → 生成账单
```

#### 5. 押金管理

- 押金作为 OneTime 收费项目（FeeCode=DEPOSIT），在"一次性收费"Tab 中展示
- 合同签署时立即生成 JE：DEBIT 112202（应收押金）/ CREDIT 2241（其他应付款-押金）
- DEPOSIT 行展开可查看押金流水记录
- 退押金：DEBIT 2241 / CREDIT 1001
- 扣款：DEBIT 2241 / CREDIT 6051

## 十五、合同模块审批闭环改造

### 15.1 改造原则

- **数据暂存**：审批通过前，数据仅存于暂存表，不入主库
- **预览确认**：执行前展示变更摘要和财务影响，用户确认后方可提交
- **审批闭环**：所有影响合同财务数据的操作都经过审批工作流
- **恢复操作**：不涉及新增数据，直接执行，无需审批

### 15.2 操作与审批对照表

| # | 操作 | 审批类型 | 当前状态 | 改造要点 |
|---|------|---------|---------|---------|
| 1 | 费用调价 | CONTRACT_FEE_CHANGE | 已有审批，补充统一暂存+预览 | 无审批路径改为暂存→自动审批 |
| 2 | 续签 | CONTRACT_RENEW | ✅ 已有完整流程 | 不动 |
| 3 | 终止合同 | CONTRACT_TERMINATE | ✅ 已有完整流程 | 补充预览步骤（反冲/押金） |
| 4 | 暂停 | **CONTRACT_SUSPEND** | ❌ 直接写主表 | 新增审批流 |
| 5 | 恢复 | - | ❌ 无需审批 | 不动（撤销操作） |
| 6 | 修改信息 | CONTRACT_MODIFY | ❌ 直接写主表+前端不调API | 新增审批流+修复前端bug |
| 7 | 自动续签开关 | 归入#6 | ❌ 直接PUT | 归入修改信息审批 |
| 8 | 添加费用(周期/一次性) | CONTRACT_FEE_CHANGE | ❌ 直接写主表 | 改走审批+预览 |
| 9 | 行内调价 | 路由到#1 | ❌ 绕过审批 | 改为路由到统一端点 |
| 10 | 停用/启用 | CONTRACT_FEE_CHANGE | ❌ 直接写主表 | 改走审批+预览 |
| 11 | 生成应收 | **CONTRACT_GENERATE_RECEIVABLE** | ❌ 直接写ReceivablePlan | 新增审批流+预览 |
| 12 | 补充收费 | **CONTRACT_SUPPLEMENTARY_FEE** | ❌ 直接写4张主表 | 新增审批流+预览 |

### 15.3 合同创建审批

```
合同列表页 → [新建合同] → 新建表单页
  ├─ 选择房源、租客、起止日期、付款周期、费用项目
  └─ [提交审批]（CONTRACT_CREATE）
      ├─ 审批通过 → 创建正式合同 + 初始化应收
      └─ 审批驳回 → 暂存标记驳回，主表无数据
```

审批通过前，合同数据仅存于暂存表。审批通过后写入 `Contracts`、`ContractTenants`、`ContractFeeConfigs` 主表。

### 15.4 初始化应收

合同审批通过、状态变为 Active 后自动触发，从合同起租月到当前月逐月生成：
- `ReceivablePlan` — 应收计划（按天分摊）
- `Voucher(ContractActivation) + JournalEntry` — 会计凭证（D 1122 / C 6001）
- 一次性费用（押金等）调 `GenerateOneTimeAsync` 处理
- 同一合同+账期不重复生成（幂等）
