# 后端框架搭建与调用完整案例（.NET 10 + Dapper 分层架构）

> 本文是《[前端框架搭建与调用完整案例](./前端框架搭建与调用完整案例.md)》的**后端姊妹篇**。
> 前端那份解决「页面怎么跑起来」，这份解决「页面背后的接口从哪来」。

## 这份文档是什么

以本仓库的 `src/` 后端为蓝本，从空目录开始，**按顺序手写**出一个能跑的分层后端骨架，
再往上落**一个完整业务模块（房型管理）**，最后和前端那份文档**严丝合缝地对接**。

- 本文的代码是**精简骨架**，不是 `src/` 的全量复刻。裁剪了什么、为什么裁，见 [1.4](#14-精简说明本案例省掉了什么)。
- 骨架之外的每一处与本仓库 `src/` 的差异，都在 [附录 A](#附录-a本案例--src-文件对照) 里逐一对照，方便你回头读真实代码。
- **业务模块刻意选了「房型管理」** —— 因为前端文档第 3 章用的就是它。两份文档的接口、字段、权限码完全一致，可以一边敲一边联调。

# 第 0 章 环境与依赖

## 0.1 前置条件

| 组件 | 版本 / 说明 | 验证命令 |
|---|---|---|
| .NET SDK | **10.0**（本项目全部 `TargetFramework` 都是 `net10.0`） | `dotnet --version` → `10.0.x` |
| SQL Server | 2019+ / LocalDB 都可以；本仓库脚本用的是 SQL Server 语法 | `sqlcmd -S . -U sa -P 你的密码 -C -Q "SELECT @@VERSION"` |
| 数据库 | 已经跑过 `scripts/Init.sql` + `scripts/SeedBase.sql`（见 [3.2](#32-第-1-步准备数据库)） | 见 [1.3](#13-启动自检) |
| 登录账号 | **`admin` / `123456`**（★ 见下方说明） | 见 1.3 第 5 步 |
| 前端 | 可选。要联调就用前端文档搭好的工程 | `npm run dev` → 5173 |

### ★ 登录密码是 `123456`，不是 `admin123`

这条单独列出来，因为**它是你照着文档敲到一半最可能卡住的地方**。

- `scripts/SeedBase.sql` 里 admin 的哈希是 `$2b$12$ZnELF2QgBXIilzbMir2uh.RWwIZYXExVvq4camCr.tNfzPH7SShk.`，
  它对应的明文经实测是 **`123456`**。
- 验证方式（两种都做过，结论一致）：
  1. 用 BCrypt.Net 的 `BCrypt.Verify("123456", 哈希)` → 通过；`BCrypt.Verify("admin123", 哈希)` → 不通过；
  2. 直接打后端接口：`POST /api/auth/login` 传 `123456` → **200 + token**；传 `admin123` → **401「用户名或密码错误」**。
- ⚠️ **早期版本的登录页和文档曾写成 `admin123`，现已全部统一为 `123456`。**
  如果看到的页面或文档仍写着 `admin123`，说明是旧版本，以本文为准。

**想换成自己的密码？** 用 BCrypt 生成哈希再 UPDATE 就行：

```bash
# ① 生成哈希（work factor 用 12，和种子里的一致）
mkdir pwgen && cd pwgen
dotnet new console -o .
dotnet add package BCrypt.Net-Next --version 4.2.0
# 把 Program.cs 内容换成这一行：
#   Console.WriteLine(BCrypt.Net.BCrypt.HashPassword("你的新密码", 12));
dotnet run
```

```sql
-- ② 写回数据库
UPDATE [Users] SET [PasswordHash] = '$2b$12$新生成的哈希' WHERE [Username] = 'admin';
```

> **顺带说一句**：`BCrypt.HashPassword` 每次生成的哈希都不一样（自带随机盐），
> 所以**不能**用"哈希字符串相不相等"来判断密码是否相同 —— 只能用 `BCrypt.Verify(明文, 哈希)`。
> 这一点在排查"我明明改对密码了却登录不上"时特别重要。

> **为什么不用 EF Core？** 本项目的架构选择是 **Dapper + 手写 SQL**：
> 实体是带行为的「富领域模型」，SQL 全部集中在 `SqlMaps.xml`，由 DBA 也能看懂、能改。
> 代价是没有 EF 的变更追踪和 LINQ —— 所以项目自己实现了一个 **UnitOfWork + ChangeTracker**
> （见 [2.4](#24-写库链新增--修改--删除三种走向)），这是本文最值得看的部分之一。

## 0.2 创建四个项目

在一个**空目录**里执行（注意顺序：Core 在最前，Api 在最后，因为依赖方向是单向的）：

```bash
# ① 解决方案（可选，但建议有，方便一次 dotnet build 全编）
dotnet new sln -n RentalBillingSystem

# ② 四个项目（-f net10.0 固定框架版本）
dotnet new classlib -n RBS.Core           -o src/RBS.Core           -f net10.0
dotnet new classlib -n RBS.Application    -o src/RBS.Application    -f net10.0
dotnet new classlib -n RBS.Infrastructure -o src/RBS.Infrastructure -f net10.0
dotnet new webapi   -n RBS.Api            -o src/RBS.Api            -f net10.0

# ③ 挂到解决方案上
dotnet sln add src/RBS.Core src/RBS.Application src/RBS.Infrastructure src/RBS.Api

# ④ 建立项目引用（★ 这一步决定了架构：依赖只能朝右指向更低层）
dotnet add src/RBS.Application/RBS.Application.csproj       reference src/RBS.Core/RBS.Core.csproj
dotnet add src/RBS.Infrastructure/RBS.Infrastructure.csproj reference src/RBS.Core/RBS.Core.csproj
dotnet add src/RBS.Infrastructure/RBS.Infrastructure.csproj reference src/RBS.Application/RBS.Application.csproj
dotnet add src/RBS.Api/RBS.Api.csproj                       reference src/RBS.Core/RBS.Core.csproj
dotnet add src/RBS.Api/RBS.Api.csproj                       reference src/RBS.Application/RBS.Application.csproj
dotnet add src/RBS.Api/RBS.Api.csproj                       reference src/RBS.Infrastructure/RBS.Infrastructure.csproj
```

四条 `reference` 规则可以总结成一句话：

```
RBS.Api ──→ RBS.Infrastructure ──→ RBS.Application ──→ RBS.Core
    └──────────────────────────────────────────────────────┘
                     （Api 也能直接用 Core 和 Application）
```

`RBS.Core` **不引用任何项目、不引用任何包** —— 这是分层架构的硬约束。
如果哪天你发现 `RBS.Core` 里出现了 `using Microsoft.Data.SqlClient;`，那就是架构破了。

> `dotnet new webapi` 会顺手生成 `WeatherForecast` 示例，**删掉它**
> （`src/RBS.Api/Program.cs` 会被我们在第 36 步整份覆盖，不用管）。
> 同时删掉四个项目里默认生成的 `Class1.cs`。

                        │  ── 只做协议转换，不写业务规则 ──     │
                        └───────────────┬──────────────────────┘
                                        │
              ┌─────────────────────────┴─────────────────────────┐
              ▼                                                   ▼
┌───────────────────────────────┐                 ┌────────────────────────────────┐
│  RBS.Application（应用层）     │                 │  RBS.Infrastructure（基础设施）│
│  DTO / Service / 事务编排      │◀────────────────│  Dapper 仓储 / SqlLoader /     │
│  ── 不碰 HttpContext ──        │   实现其接口     │  AuditLogWriter / TenantService │
└───────────────┬───────────────┘                 └───────────────┬────────────────┘
                │                                                  │
                └──────────────────────┬───────────────────────────┘
                                       ▼
                    ┌──────────────────────────────────────┐
                    │         RBS.Core（领域层）            │
                    │  实体 + 值对象 + 全部接口定义          │
                    │  ── 不引用任何项目 / 任何包 ──         │
                    └──────────────────────────────────────┘
```

三条**铁律**（第 4 章会反复用到）：

1. **依赖只能向下**：上层知道下层，下层**不知道**上层。
   `RoomTypeService` 能 `using RBS.Core...`；`RoomType` 绝不能 `using RBS.Application...`。
2. **Core 定义接口，Infrastructure 实现接口**。所以 Core 里 `IRepository<T>` 是接口，
   Infrastructure 里 `DapperRepository<T>` 是实现 —— 将来要换 PostgreSQL，只动 Infrastructure。
3. **业务规则写在实体里，不写在 Service 里**。
   `RoomType.Rename()` 自己校验名称非空并 `throw ArgumentException`，
   Service 只负责「把它取出来 → 调用 → 提交」。这就是为什么实体属性的 setter 全是 `private set`。

### 第 2 步 `src/RBS.Core/Common/ChinaTime.cs`

```csharp
namespace RBS.Core.Common;

/// <summary>
/// 中国标准时间（CST, UTC+8）工具类
///
/// 为什么要有它：服务器可能部署在任何时区（容器里默认 UTC），
/// 如果业务代码里到处写 DateTime.Now，换个部署环境时间就整体偏 8 小时。
/// 所以本项目的约定是：**所有时间戳都走 ChinaTime.Now**。
/// </summary>
public static class ChinaTime
{
    /// <summary>中国标准时区（Windows: "China Standard Time"，Linux: "Asia/Shanghai"）</summary>
    private static readonly TimeZoneInfo ChinaTz =
        TimeZoneInfo.FindSystemTimeZoneById("China Standard Time");

    /// <summary>当前中国标准时间（从 UTC 换算，不受服务器本地时区影响）</summary>
    public static DateTime Now => TimeZoneInfo.ConvertTimeFromUtc(DateTime.UtcNow, ChinaTz);

    /// <summary>当前中国标准日期（时间归零）</summary>
    public static DateTime Today => Now.Date;
}
```

> **Linux 容器注意**：`FindSystemTimeZoneById("China Standard Time")` 在 Linux 上会抛异常，
> 真实项目 `src/` 里用的是同一个 id，靠的是容器里带 tzdata（或 `TZ=Asia/Shanghai`）。
> 如果你在 Linux 上跑本案例报 `TimeZoneNotFoundException`，改成 `"Asia/Shanghai"` 即可。

### 第 3 步 `src/RBS.Core/Entities/Base/AuditableEntity.cs`

> **全项目最重要的一个文件**。所有实体都继承它；它同时决定了
> 「审计字段从哪来」（第 2.5 节）和「反射生成 SQL 时有哪些列」（第 2.4 节）。

```csharp
namespace RBS.Core.Entities.Base;

/// <summary>
/// 可审计实体基类 —— 所有需要落库的实体都继承它
///
/// 它提供两样东西：
///   1. Id：构造时自动生成 GUID（分布式环境下不需要数据库自增）
///   2. 8 个审计字段：谁在什么时候、从哪个 IP / 哪台机器创建的，最后一次修改是谁改的
/// </summary>
public abstract class AuditableEntity
{
    /// <summary>主键</summary>
    public Guid Id { get; protected set; }

    // ===== 创建审计（首次插入时写入，非空）=====
    /// <summary>创建人用户 ID</summary>
    public Guid CreatedBy { get; protected set; }
    /// <summary>创建时间（东八区）</summary>
    public DateTime CreatedAt { get; protected set; }
    /// <summary>创建时客户端 IP</summary>
    public string? CreatedIp { get; protected set; }
    /// <summary>创建时客户端主机名</summary>
    public string? CreatedHostname { get; protected set; }

    // ===== 修改审计（发生过更新才有值，可空）=====
    /// <summary>最后修改人用户 ID</summary>
    public Guid? UpdatedBy { get; protected set; }
    /// <summary>最后修改时间</summary>
    public DateTime? UpdatedAt { get; protected set; }
    /// <summary>修改时客户端 IP</summary>
    public string? UpdatedIp { get; protected set; }
    /// <summary>修改时客户端主机名</summary>
    public string? UpdatedHostname { get; protected set; }

    /// <summary>构造时生成主键、打上创建时间 —— 子类不用管这两件事</summary>
    protected AuditableEntity()
    {
        Id = Guid.NewGuid();
        CreatedAt = RBS.Core.Common.ChinaTime.Now;
    }

    /// <summary>设置创建审计信息（由审计装饰器在 INSERT 前调用）</summary>
    public void SetCreated(Guid userId, DateTime time, string? ip, string? hostname)
    {
        CreatedBy = userId;
        CreatedAt = time;
        CreatedIp = ip;
        CreatedHostname = hostname;
    }

    /// <summary>设置修改审计信息（由审计装饰器在 UPDATE 前调用）</summary>
    public void SetUpdated(Guid userId, DateTime time, string? ip, string? hostname)
    {
        UpdatedBy = userId;
        UpdatedAt = time;
        UpdatedIp = ip;
        UpdatedHostname = hostname;
    }
}
```

### 第 8 步 `src/RBS.Core/Interfaces/Repositories/IRepository.cs`

> 一个文件里放两个类型：泛型仓储接口 + 分页信封 `PagedResult<T>`。
> `PagedResult<T>` 就是前端文档 §3.8 提到的那个 `{items,total,page,pageSize,totalPages}`。

```csharp
using RBS.Core.Entities.Base;

namespace RBS.Core.Interfaces.Repositories;

/// <summary>
/// 泛型仓储接口 —— 提供最基本的 CRUD 契约
///
/// 设计取舍：
///   - 只提供「按 Id 查」「查全部」「增」「改」「删」「是否存在」
///   - **不提供 LINQ 表达式分页**：手写 SQL 的架构下，复杂查询应该走
///     特化仓储 + SqlMaps.xml，而不是把 SQL 泄漏到领域层（见 4.1）
/// </summary>
public interface IRepository<T> where T : AuditableEntity
{
    Task<T?> GetByIdAsync(Guid id, CancellationToken ct = default);
    Task<List<T>> GetAllAsync(CancellationToken ct = default);
    Task<T> AddAsync(T entity, CancellationToken ct = default);
    Task UpdateAsync(T entity, CancellationToken ct = default);
    Task DeleteAsync(T entity, CancellationToken ct = default);
    Task<bool> ExistsAsync(Guid id, CancellationToken ct = default);
}

/// <summary>
/// 分页结果信封 —— 所有分页接口统一返回这个形状
/// 序列化后：{ "items": [...], "total": 128, "page": 1, "pageSize": 20, "totalPages": 7 }
/// </summary>
public class PagedResult<T>
{
    /// <summary>当前页数据</summary>
    public List<T> Items { get; set; } = new();
    /// <summary>总记录数</summary>
    public int Total { get; set; }
    /// <summary>当前页码（从 1 开始）</summary>
    public int Page { get; set; }
    /// <summary>每页条数</summary>
    public int PageSize { get; set; }
    /// <summary>总页数</summary>
    public int TotalPages { get; set; }
}
```

### 第 15 步 `src/RBS.Infrastructure/Data/SqlMaps/SqlLoader.cs`

```csharp
using System.Xml.Linq;
using RBS.Core.Interfaces.Persistence;

namespace RBS.Infrastructure.Data.SqlMaps;

/// <summary>
/// SQL 映射加载器 —— 启动时一次性把 SqlMaps.xml 读进内存（单例，之后只读）
///
/// 三个「启动即失败」（Fail-Fast）校验，把错误提前到启动阶段：
///   1. 元素缺 id 属性
///   2. id 不符合 {模块}.{CRUD}.{实体}.{描述}，或 CRUD 不是那四个动词
///   3. id 重复
/// 这样就不用等到线上某个接口被调用时才发现 SQL 写错了。
/// </summary>
public class SqlLoader : ISqlLoader
{
    private readonly Dictionary<string, string> _sqlMap;
    private static readonly HashSet<string> ValidCrud = new(StringComparer.OrdinalIgnoreCase)
        { "Select", "Insert", "Update", "Delete" };

    public SqlLoader(string xmlFilePath)
    {
        var doc = XDocument.Load(xmlFilePath);
        // 大小写不敏感：调用方写 select 也能取到 Select 的那条
        _sqlMap = new Dictionary<string, string>(StringComparer.OrdinalIgnoreCase);

        foreach (var el in doc.Root!.Elements())
        {
            var id = el.Attribute("id")?.Value
                ?? throw new InvalidOperationException($"SqlMaps.xml 中存在缺少 id 属性的元素：{el.Name.LocalName}");

            var parts = id.Split('.');
            if (parts.Length < 4 || !ValidCrud.Contains(parts[1]))
                throw new InvalidOperationException(
                    $"SqlMaps.xml 中 id \"{id}\" 不符合命名规范：应为 {{模块}}.{{CRUD}}.{{实体}}.{{描述}}，"
                    + "CRUD 必须为 Select/Insert/Update/Delete");

            if (!_sqlMap.TryAdd(id, el.Value.Trim()))
                throw new InvalidOperationException($"SqlMaps.xml 中存在重复的 id：\"{id}\"");
        }

        if (_sqlMap.Count == 0)
            throw new InvalidOperationException("SqlMaps.xml 中未找到任何 SQL 映射");
    }

    public string Get(string id)
        => _sqlMap.TryGetValue(id, out var sql)
            ? sql
            : throw new KeyNotFoundException($"SqlMaps.xml 中不存在 id 为 \"{id}\" 的 SQL 映射");

    public bool Contains(string id) => _sqlMap.ContainsKey(id);

    public int Count => _sqlMap.Count;
}
```

### 第 17 步 `src/RBS.Infrastructure/Data/Services/AuditLogWriter.cs`

> **审计链的核心。** 三个关键设计，每一条都值得记住：
> ① **独立连接**：不复用业务事务的连接；② **失败只 Warning**：审计写不进去不能拖垮业务；
> ③ **版本号自增**：`MAX(AuditVersionNo)+1`，一条记录改 10 次就有 10 条历史。

```csharp
using Microsoft.Data.SqlClient;
using Microsoft.Extensions.Logging;
using RBS.Core.Common;
using RBS.Core.Interfaces.Services;

namespace RBS.Infrastructure.Data.Services;

/// <summary>审计日志写入器 —— 把变更快照写进 {表名}_Audit</summary>
public class AuditLogWriter : IAuditLogWriter
{
    private readonly string _connectionString;
    private readonly ILogger<AuditLogWriter> _logger;

    public AuditLogWriter(string connectionString, ILogger<AuditLogWriter> logger)
    {
        _connectionString = connectionString;
        _logger = logger;
    }

    public async Task LogChangesAsync(string tableName, string entityId, string action,
        Dictionary<string, object?> changes, Guid changedBy, CancellationToken ct = default)
    {
        var auditTableName = $"{tableName}_Audit";

        try
        {
            // ---- 列名与参数：前 5 列是审计元数据，后面是实体字段 ----
            var columns = new List<string> { "[Id]", "[AuditAction]", "[AuditVersionNo]", "[AuditChangedAt]", "[AuditChangedBy]" };
            var paramRefs = new List<string> { "@p0", "@p1", "@nextVer", "@p2", "@p3" };
            var args = new List<object?> { entityId, action, ChinaTime.Now, changedBy };

            string? hostname = null;
            foreach (var kv in changes)
            {
                if (kv.Key == "Id") continue;   // Id 已经作为第 1 列写过了
                if (hostname == null &&
                    kv.Key is "CreatedHostname" or "UpdatedHostname")
                    hostname = kv.Value?.ToString();

                columns.Add($"[{kv.Key}]");
                args.Add(kv.Value);
                paramRefs.Add($"@p{args.Count - 1}");
            }
            if (hostname != null)
            {
                columns.Add("[AuditChangedHostname]");
                paramRefs.Add("@hostname");
            }

            // ---- @nextVer：同一实体在审计表里的下一个版本号 ----
            var sql = $@"
DECLARE @nextVer INT = ISNULL((SELECT MAX(AuditVersionNo) FROM [{auditTableName}] WHERE [Id] = @p0), 0) + 1;
IF EXISTS (SELECT 1 FROM sys.tables WHERE name = @tableName)
    INSERT INTO [{auditTableName}] ({string.Join(", ", columns)})
    VALUES ({string.Join(", ", paramRefs)});";

            await using var conn = new SqlConnection(_connectionString);
            await conn.OpenAsync(ct);
            await using var cmd = new SqlCommand(sql, conn);
            // 审计表可能不存在（不是每个表都要审计）→ 用 sys.tables 判断，静默跳过
            cmd.Parameters.AddWithValue("@tableName", auditTableName);
            for (int i = 0; i < args.Count; i++)
                cmd.Parameters.AddWithValue($"@p{i}", args[i] ?? DBNull.Value);
            if (hostname != null)
                cmd.Parameters.AddWithValue("@hostname", hostname);

            await cmd.ExecuteNonQueryAsync(ct);
        }
        catch (Exception ex)
        {
            // ★ 关键：审计失败绝不能影响业务 —— 只记 Warning
            _logger.LogWarning(ex, "审计写入失败（不影响主操作）：Table={AuditTable}, Id={EntityId}, Action={Action}",
                auditTableName, entityId, action);
        }
    }
}
```

> 真实版还多一个 `AuditChangedFields` 列（记录本次改了哪几个字段，前端审计页可以高亮显示），
> 实现方式是读上一版本做逐字段比对。本案例省掉，见 [1.4](#14-精简说明本案例省掉了什么)。

### 第 18 步 `src/RBS.Infrastructure/Data/Services/RepositoryAuditService.cs`

> **审计装饰器。** 仓储自己完全不写审计代码，全部委托给它 —— 这就是为什么
> `DapperRepository` 里只有 `_auditService.PopulateCreatedFields(entity)` 这种一行调用。

```csharp
using RBS.Core.Common;
using RBS.Core.Interfaces.Services;

namespace RBS.Infrastructure.Data.Services;

/// <summary>
/// 审计装饰器 —— 统一封装所有仓储的审计逻辑
///
/// 它回答两个问题：
///   1. INSERT / UPDATE 前，往实体的审计字段里填什么？（PopulateXxxFields）
///   2. 审计日志的「操作人」是谁？（ResolveUserId）
///
/// 操作人优先级：实体.UpdatedBy → 当前登录用户(JWT) → 实体.CreatedBy → Guid.Empty
/// 最后的 Guid.Empty 是给后台定时任务用的（没有登录上下文）。
/// </summary>
public class RepositoryAuditService
{
    private readonly IAuditLogWriter _auditWriter;
    private readonly IClientInfoService? _clientInfo;
    private readonly ICurrentUserService? _currentUser;

    public RepositoryAuditService(IAuditLogWriter auditWriter,
        IClientInfoService? clientInfo = null, ICurrentUserService? currentUser = null)
    {
        _auditWriter = auditWriter;
        _clientInfo = clientInfo;
        _currentUser = currentUser;
    }

    /// <summary>INSERT 前调用：填 CreatedIp / CreatedHostname / CreatedBy</summary>
    public void PopulateCreatedFields<T>(T entity)
    {
        if (_clientInfo != null)
        {
            TrySetIfNull(entity, "CreatedIp", _clientInfo.GetClientIp());
            TrySetIfNull(entity, "CreatedHostname", _clientInfo.GetClientHostname());
        }
        // 实体自己没设 CreatedBy 时，用当前登录用户兜底
        if (_currentUser == null || _currentUser.UserId == Guid.Empty) return;
        var prop = typeof(T).GetProperty("CreatedBy");
        if (prop?.CanWrite == true && prop.GetValue(entity) is Guid g && g == Guid.Empty)
            prop.SetValue(entity, _currentUser.UserId);
    }

    /// <summary>UPDATE 前调用：填 UpdatedBy / UpdatedAt / UpdatedIp / UpdatedHostname</summary>
    public void PopulateUpdatedFields<T>(T entity)
    {
        var uid = _currentUser?.UserId ?? Guid.Empty;
        if (uid != Guid.Empty) TrySet(entity, "UpdatedBy", uid);
        TrySet(entity, "UpdatedAt", ChinaTime.Now);
        if (_clientInfo != null)
        {
            TrySet(entity, "UpdatedIp", _clientInfo.GetClientIp());
            TrySet(entity, "UpdatedHostname", _clientInfo.GetClientHostname());
        }
    }

    /// <summary>写 Create 审计</summary>
    public Task WriteCreateLogAsync<T>(string tableName, T entity, CancellationToken ct = default)
        => _auditWriter.LogChangesAsync(tableName, GetEntityId(entity), "Create",
            EntityToDict(entity), ResolveUserId(entity, useUpdated: false), ct);

    /// <summary>写 Update 审计</summary>
    public Task WriteUpdateAsync<T>(string tableName, T entity, CancellationToken ct = default)
        => _auditWriter.LogChangesAsync(tableName, GetEntityId(entity), "Update",
            EntityToDict(entity), ResolveUserId(entity, useUpdated: true), ct);

    /// <summary>写 Delete 审计（传的是删除**之前**的快照）</summary>
    public Task WriteDeleteAsync<T>(string tableName, T entity, CancellationToken ct = default)
        => _auditWriter.LogChangesAsync(tableName, GetEntityId(entity), "Delete",
            EntityToDict(entity), ResolveUserId(entity, useUpdated: true), ct);

    /// <summary>取客户端 IP/主机名（UoW 的 CommitAsync 也要用）</summary>
    public (string? ip, string? hostname) GetClientInfo()
        => (_clientInfo?.GetClientIp(), _clientInfo?.GetClientHostname());

    // ===== 内部工具 =====

    private Guid ResolveUserId<T>(T entity, bool useUpdated)
    {
        if (useUpdated && TryGetGuid(entity, "UpdatedBy") is Guid ub && ub != Guid.Empty) return ub;
        if (_currentUser?.UserId is Guid uid && uid != Guid.Empty) return uid;
        if (TryGetGuid(entity, "CreatedBy") is Guid cb && cb != Guid.Empty) return cb;
        return Guid.Empty;
    }

    private static string GetEntityId<T>(T entity)
        => typeof(T).GetProperty("Id")?.GetValue(entity)?.ToString() ?? Guid.Empty.ToString();

    // ★ 这三个工具方法的参数写成 object? 并加空判断：
    //   调用方传进来的 T 是无约束泛型（可能是引用类型、也可能为 null），
    //   参数写成非空的 object 会让编译器报 CS8604（可能为 null 的实参）。
    private static Guid? TryGetGuid(object? entity, string propName)
        => entity == null ? null : entity.GetType().GetProperty(propName)?.GetValue(entity) as Guid?;

    private static void TrySet(object? entity, string propName, object? value)
    {
        if (entity == null) return;
        var prop = entity.GetType().GetProperty(propName);
        if (prop?.CanWrite == true) prop.SetValue(entity, value);
    }

    private static void TrySetIfNull(object? entity, string propName, object? value)
    {
        if (entity == null) return;
        var prop = entity.GetType().GetProperty(propName);
        if (prop?.CanWrite == true && prop.GetValue(entity) == null) prop.SetValue(entity, value);
    }

    /// <summary>
    /// 实体 → 字段字典（反射）。审计表和 UoW 的差异比对都用它。
    /// 排除导航属性（集合类型）和领域事件，只留真正落库的标量字段。
    /// </summary>
    internal static Dictionary<string, object?> EntityToDict<T>(T entity)
    {
        ArgumentNullException.ThrowIfNull(entity);
        var dict = new Dictionary<string, object?>();
        foreach (var p in typeof(T).GetProperties(System.Reflection.BindingFlags.Public | System.Reflection.BindingFlags.Instance))
        {
            if (p.Name == "DomainEvents") continue;
            if (!p.CanWrite) continue;
            if (IsNavProp(p)) continue;
            dict[p.Name] = p.GetValue(entity);
        }
        return dict;
    }

    private static bool IsNavProp(System.Reflection.PropertyInfo p)
    {
        var t = p.PropertyType;
        if (t.IsGenericType && t.GetGenericTypeDefinition() == typeof(Nullable<>)) return false;
        return t == typeof(System.Collections.IList) || t.IsGenericType
               || p.Name is "DomainEvents" or "Records" or "Roles";
    }
}

### 第 20 步 `src/RBS.Infrastructure/Data/Repositories/DapperRepository.cs`

> ★★★ **全项目技术含量最高的文件。** 一个泛型类支撑了 30+ 张简单字典表的 CRUD。
> 读完它，你会明白这套架构「为什么不需要为每张表写一个仓储」。

```csharp
using System.Reflection;
using Dapper;
using RBS.Core.Entities.Base;
using RBS.Core.Interfaces.Persistence;
using RBS.Core.Interfaces.Repositories;
using RBS.Core.Interfaces.Services;
using RBS.Infrastructure.Data.Services;

namespace RBS.Infrastructure.Data.Repositories;

/// <summary>
/// Dapper 泛型仓储 —— 用反射生成 INSERT / UPDATE / SELECT，覆盖所有「简单字典表」
///
/// 它做对了三件容易做错的事：
///   ① 表名推断：RoomType → RoomTypes（见 InferTableName）
///   ② 列名 = 实体属性名：所以实体属性和数据库列必须一一对应
///   ③ 审计字段排除规则：INSERT 不带 Updated*，UPDATE 不带 Id/Created*
/// </summary>
public class DapperRepository<T> : IRepository<T> where T : AuditableEntity
{
    protected readonly IDbConnectionFactory _db;
    protected readonly string _tableName;
    protected readonly IChangeTracker? _tracker;
    protected readonly ITenantService? _tenant;
    protected readonly RepositoryAuditService _auditService;

    public DapperRepository(IDbConnectionFactory db, IAuditLogWriter auditWriter,
        string? tableName = null, IChangeTracker? tracker = null,
        ITenantService? tenant = null, RepositoryAuditService? auditService = null)
    {
        _db = db;
        _auditService = auditService ?? new RepositoryAuditService(auditWriter);
        _tracker = tracker;
        _tableName = tableName ?? InferTableName();   // 也可以显式传表名覆盖
        _tenant = tenant;
    }

    /// <summary>
    /// 判断这次查询是否要加 AND CompanyId=@CompanyId
    /// 两个条件同时满足才加：① 有租户上下文且能确定公司；② 实体声明了 IHasCompany
    /// → 房型（RoomType）不实现 IHasCompany，所以永远不会被过滤
    /// </summary>
    private bool HasCompanyFilter([System.Diagnostics.CodeAnalysis.NotNullWhen(true)] out Guid companyId)
    {
        companyId = Guid.Empty;
        if (_tenant == null) return false;
        var cid = _tenant.EffectiveCompanyId;
        if (cid == null) return false;                                   // 超管看全部
        if (!typeof(IHasCompany).IsAssignableFrom(typeof(T))) return false; // 实体不隔离
        companyId = cid.Value;
        return true;
    }

    public async Task<T?> GetByIdAsync(Guid id, CancellationToken ct = default)
    {
        using var conn = _db.CreateConnection();
        conn.Open();
        T? entity = HasCompanyFilter(out var cid)
            ? await conn.QuerySingleOrDefaultAsync<T>($"SELECT * FROM [{_tableName}] WHERE Id=@Id AND CompanyId=@CompanyId", new { Id = id, CompanyId = cid })
            : await conn.QuerySingleOrDefaultAsync<T>($"SELECT * FROM [{_tableName}] WHERE Id=@Id", new { Id = id });

        // ★ 从数据库读出来的实体立刻登记快照，后面改了才能被 CommitAsync 发现
        if (entity != null) _tracker?.Track(entity, _tableName);
        return entity;
    }

    public async Task<List<T>> GetAllAsync(CancellationToken ct = default)
    {
        using var conn = _db.CreateConnection();
        conn.Open();
        List<T> list = HasCompanyFilter(out var cid)
            ? (await conn.QueryAsync<T>($"SELECT * FROM [{_tableName}] WHERE CompanyId=@CompanyId", new { CompanyId = cid })).ToList()
            : (await conn.QueryAsync<T>($"SELECT * FROM [{_tableName}]")).ToList();

        foreach (var e in list) _tracker?.Track(e, _tableName);
        return list;
    }

    public async Task<T> AddAsync(T entity, CancellationToken ct = default)
    {
        // ① 审计装饰器：INSERT 之前把 CreatedBy/CreatedIp/CreatedHostname 填好
        _auditService.PopulateCreatedFields(entity);

        // ② 反射出所有要写的列（排除 Updated* 和导航属性）
        var exclude = new HashSet<string> { "UpdatedBy", "UpdatedAt", "UpdatedIp", "UpdatedHostname" };
        var props = typeof(T)
            .GetProperties(BindingFlags.Public | BindingFlags.Instance)
            .Where(p => p.CanRead && !exclude.Contains(p.Name) && !IsNavProp(p))
            .Select(p => p.Name)
            .ToList();

        var cols = string.Join(",", props);
        var vals = string.Join(",", props.Select(p => "@" + p));

        using var conn = _db.CreateConnection();
        conn.Open();
        await conn.ExecuteAsync($"INSERT INTO [{_tableName}] ({cols}) VALUES ({vals})", entity);

        // ③ 写 Create 审计（独立连接，失败不影响业务）
        await _auditService.WriteCreateLogAsync(_tableName, entity, ct);
        _tracker?.Track(entity, _tableName);
        return entity;
    }

    public async Task UpdateAsync(T entity, CancellationToken ct = default)
    {
        // 先读旧值：审计日志需要「改之前长什么样」，而且只有读到了才写审计
        var oldEntity = await GetByIdAsync(GetEntityGuidId(entity), ct);

        _auditService.PopulateUpdatedFields(entity);

        var exclude = new HashSet<string> { "Id", "CreatedBy", "CreatedAt", "CreatedIp", "CreatedHostname" };
        var sets = string.Join(",",
            typeof(T).GetProperties(BindingFlags.Public | BindingFlags.Instance)
                .Where(p => p.CanRead && p.CanWrite && !exclude.Contains(p.Name) && !IsNavProp(p))
                .Select(p => $"[{p.Name}]=@{p.Name}"));

        using var conn = _db.CreateConnection();
        conn.Open();
        await conn.ExecuteAsync($"UPDATE [{_tableName}] SET {sets} WHERE Id=@Id", entity);

        if (oldEntity != null)
            await _auditService.WriteUpdateAsync(_tableName, entity, ct);
    }

    public async Task DeleteAsync(T entity, CancellationToken ct = default)
    {
        var oldEntity = await GetByIdAsync(GetEntityGuidId(entity), ct);
        var id = GetEntityGuidId(entity);

        using var conn = _db.CreateConnection();
        conn.Open();
        await conn.ExecuteAsync($"DELETE FROM [{_tableName}] WHERE Id=@Id", new { Id = id });

        // 物理删除之后，审计表里的这条记录就是唯一的「遗照」了
        if (oldEntity != null)
            await _auditService.WriteDeleteAsync(_tableName, oldEntity, ct);
    }

    public async Task<bool> ExistsAsync(Guid id, CancellationToken ct = default)
    {
        using var conn = _db.CreateConnection();
        conn.Open();
        if (HasCompanyFilter(out var cid))
            return await conn.QuerySingleAsync<int>($"SELECT COUNT(1) FROM [{_tableName}] WHERE Id=@Id AND CompanyId=@CompanyId", new { Id = id, CompanyId = cid }) > 0;
        return await conn.QuerySingleAsync<int>($"SELECT COUNT(1) FROM [{_tableName}] WHERE Id=@Id", new { Id = id }) > 0;
    }

    private static Guid GetEntityGuidId(T entity)
        => typeof(T).GetProperty("Id")?.GetValue(entity) is Guid g ? g : Guid.Empty;

    /// <summary>判断是否是导航属性（集合类型 / 领域事件），这些不能当列写进 SQL</summary>
    private static bool IsNavProp(PropertyInfo p)
    {
        var t = p.PropertyType;
        // Nullable<T> 不是导航属性（注意顺序：先排掉 Nullable 再判 IsGenericType）
        if (t.IsGenericType && t.GetGenericTypeDefinition() == typeof(Nullable<>)) return false;
        return t == typeof(System.Collections.IList) || t.IsGenericType
               || p.Name is "DomainEvents" or "Records" or "Roles";
    }

    /// <summary>
    /// 实体名 → 表名（简单复数化，够用即可）
    /// RoomType → RoomTypes / Category → Categories / Address → Addresses
    /// </summary>
    private static string InferTableName()
    {
        var name = typeof(T).Name;
        if (name.EndsWith("y")) return name[..^1] + "ies";
        if (name.EndsWith("s") || name.EndsWith("ch") || name.EndsWith("sh") || name.EndsWith("x")) return name + "es";
        return name + "s";
    }
}
```

### 第 23 步 `src/RBS.Infrastructure/Data/UnitOfWork/DapperUnitOfWork.cs`

> ★★★ **第二重要的文件。** 它同时扮演两个角色：
> ① `IUnitOfWork`：对外提供仓储入口 + `CommitAsync` 事务边界；
> ② `IChangeTracker`：对内被仓储调用，负责「拍快照 / 算差异 / 发差异 UPDATE」。
>
> **一次 UPDATE 请求的完整路径**：
> `GetByIdAsync`（拍快照）→ 领域方法改属性 → `CommitAsync`（比对快照 → `UPDATE RoomTypes SET Name=@Name,UpdatedAt=@UpdatedAt... WHERE Id=@Id`）

```csharp
using Dapper;
using RBS.Core.Entities.Property;
using RBS.Core.Interfaces.Persistence;
using RBS.Core.Interfaces.Repositories;
using RBS.Core.Interfaces.Services;
using RBS.Core.Interfaces.UnitOfWork;
using RBS.Infrastructure.Data.Repositories;
using RBS.Infrastructure.Data.Services;

namespace RBS.Infrastructure.Data.UnitOfWork;

/// <summary>工作单元实现 —— 仓储聚合 + 变更追踪 + 事务提交</summary>
public class DapperUnitOfWork : IUnitOfWork, IChangeTracker
{
    private readonly IDbConnectionFactory _db;
    private readonly ISqlLoader _sql;
    private readonly IAuditLogWriter _auditWriter;
    private readonly ITenantService? _tenant;
    private readonly RepositoryAuditService _auditService;

    /// <summary>追踪表：表名 → (实体 ID → 快照)</summary>
    private readonly Dictionary<string, Dictionary<Guid, TrackedEntry>> _tracked = new();

    public DapperUnitOfWork(IDbConnectionFactory db, ISqlLoader sql, IAuditLogWriter auditWriter,
        ITenantService? tenant = null, RepositoryAuditService? auditService = null)
    {
        _db = db;
        _sql = sql;
        _auditWriter = auditWriter;
        _tenant = tenant;
        _auditService = auditService ?? new RepositoryAuditService(auditWriter);
    }

    // ===== 仓储入口：??= 延迟创建，一个请求里没用到的仓储根本不会实例化 =====
    public IUserRepository Users => _users ??= new DapperUserRepository(_db, _sql, _auditWriter, this, _auditService);
    public IRoleRepository Roles => _roles ??= new DapperRoleRepository(_db, _sql, _auditWriter, this, _auditService);
    public IRepository<RoomType> RoomTypes => _roomTypes ??= new DapperRepository<RoomType>(
        _db, _auditWriter, tracker: this, tenant: _tenant, auditService: _auditService);

    private IUserRepository? _users;
    private IRoleRepository? _roles;
    private IRepository<RoomType>? _roomTypes;

    // ==================================================================
    // IChangeTracker —— 被仓储调用，不对外
    // ==================================================================

    void IChangeTracker.Track<T>(T entity, string tableName)
    {
        var id = typeof(T).GetProperty("Id")?.GetValue(entity) is Guid g ? g : Guid.Empty;
        if (id == Guid.Empty) return;

        if (!_tracked.TryGetValue(tableName, out var entries))
            _tracked[tableName] = entries = new Dictionary<Guid, TrackedEntry>();

        // 同一个实体被读两次时，后一次覆盖（快照以最后一次读到的为准）
        entries[id] = new TrackedEntry(entity, RepositoryAuditService.EntityToDict(entity));
    }

    IReadOnlyDictionary<string, Dictionary<Guid, TrackedEntry>> IChangeTracker.DirtyEntries => _tracked;

    void IChangeTracker.Clear() => _tracked.Clear();

    // ==================================================================
    // CommitAsync —— 变更持久化的唯一入口
    // ==================================================================

    public async Task<int> CommitAsync(CancellationToken ct = default)
    {
        if (_tracked.Count == 0) return 0;   // 没有脏数据就直接返回，连数据库都不用连

        using var conn = _db.CreateConnection();
        conn.Open();
        using var tx = conn.BeginTransaction();

        try
        {
            var affected = 0;
            // 审计先攒起来，等业务事务提交成功后再写（审计表不该参与业务事务）
            var auditBatch = new List<(string tableName, string entityId, string action,
                Dictionary<string, object?> changes, Guid userId)>();

            foreach (var (tableName, entries) in _tracked)
            {
                foreach (var (id, entry) in entries)
                {
                    // ① 提交前填 Updated* 字段（让业务表的 UpdatedBy 也有值）
                    _auditService.PopulateUpdatedFields(entry.Entity);

                    // ② 与快照比对，只留下真正变化的字段
                    var now = RepositoryAuditService.EntityToDict(entry.Entity);
                    var changes = DiffDict(entry.Snapshot, now);
                    if (changes.Count == 0) continue;   // ★ 没改 → 一条 SQL 都不发

                    var sets = string.Join(",", changes.Keys.Select(k => $"[{k}]=@{k}"));
                    var parms = new DynamicParameters();
                    parms.Add("@Id", id);
                    foreach (var k in changes.Keys)
                        parms.Add($"@{k}", entry.Entity.GetType().GetProperty(k)?.GetValue(entry.Entity));

                    affected += await conn.ExecuteAsync($"UPDATE [{tableName}] SET {sets} WHERE Id=@Id", parms, tx);

                    // ③ 审计用「全量快照」而不是差异
                    var updatedBy = entry.Entity.GetType().GetProperty("UpdatedBy")?.GetValue(entry.Entity) as Guid? ?? Guid.Empty;
                    if (updatedBy == Guid.Empty)
                        updatedBy = entry.Entity.GetType().GetProperty("CreatedBy")?.GetValue(entry.Entity) as Guid? ?? Guid.Empty;

                    var (ip, hostname) = _auditService.GetClientInfo();
                    if (ip != null) now["UpdatedIp"] = ip;
                    if (hostname != null) now["UpdatedHostname"] = hostname;

                    auditBatch.Add((tableName, id.ToString(), "Update", now, updatedBy));
                }
            }

            tx.Commit();

            // ④ 事务外写审计：审计失败不影响已经提交的业务数据
            foreach (var (tn, entityId, action, changes, userId) in auditBatch)
                await _auditWriter.LogChangesAsync(tn, entityId, action, changes, userId, ct);

            _tracked.Clear();
            return affected;
        }
        catch
        {
            tx.Rollback();
            _tracked.Clear();
            throw;
        }
    }

    /// <summary>带重试的提交 —— 只对「可恢复」的 SQL 错误重试</summary>
    public async Task<int> CommitWithRetryAsync(int maxRetries = 3, CancellationToken ct = default)
    {
        for (var attempt = 1; ; attempt++)
        {
            try
            {
                return await CommitAsync(ct);
            }
            catch (InvalidOperationException)
            {
                throw;   // 业务校验失败（如状态守卫）重试多少次都一样，直接抛
            }
            catch (Exception ex) when (attempt < maxRetries && IsTransient(ex))
            {
                await Task.Delay(TimeSpan.FromMilliseconds(100 * attempt), ct);   // 退避
            }
        }
    }

    /// <summary>SQL Server 可恢复错误：死锁 1205 / 超时 -2 / 快照隔离冲突 3960</summary>
    private static bool IsTransient(Exception ex)
    {
        if (ex is Microsoft.Data.SqlClient.SqlException sqlEx) return sqlEx.Number is 1205 or -2 or 3960;
        if (ex.InnerException is Microsoft.Data.SqlClient.SqlException inner) return inner.Number is 1205 or -2 or 3960;
        return ex is TaskCanceledException or OperationCanceledException;
    }

    /// <summary>逃生舱：执行原生 SQL（参数自动命名 @p0、@p1…）</summary>
    public async Task<int> ExecuteSqlRawAsync(string sql, object parameters, CancellationToken ct = default)
    {
        using var conn = _db.CreateConnection();
        conn.Open();
        return await conn.ExecuteAsync(sql, new DynamicParameters(parameters));
    }

    public void Dispose() => _tracked.Clear();

    /// <summary>比对快照与当前值，返回发生变化的字段</summary>
    private static Dictionary<string, object?> DiffDict(
        Dictionary<string, object?> snapshot, Dictionary<string, object?> now)
    {
        var changed = new Dictionary<string, object?>();
        foreach (var kv in now)
        {
            if (!snapshot.TryGetValue(kv.Key, out var oldValue) || !Equals(oldValue, kv.Value))
                changed[kv.Key] = kv.Value;
        }
        return changed;
    }
}

### 第 24 步 `src/RBS.Infrastructure/Data/DependencyInjection.cs`

> **Infrastructure 层的唯一出口**：Api 只需要调一句 `AddInfrastructureData(configuration)`。

```csharp
using Microsoft.Extensions.Configuration;
using Microsoft.Extensions.DependencyInjection;
using Microsoft.Extensions.Logging;
using RBS.Core.Interfaces.Persistence;
using RBS.Core.Interfaces.Services;
using RBS.Core.Interfaces.UnitOfWork;
using RBS.Infrastructure.Data.Repositories;
using RBS.Infrastructure.Data.Services;
using RBS.Infrastructure.Data.SqlMaps;
using RBS.Infrastructure.Data.UnitOfWork;

namespace RBS.Infrastructure.Data;

/// <summary>基础设施层依赖注入</summary>
public static class DependencyInjection
{
    public static IServiceCollection AddInfrastructureData(
        this IServiceCollection services, IConfiguration configuration)
    {
        var connectionString = configuration.GetConnectionString("DefaultConnection")
            ?? throw new InvalidOperationException("未配置连接字符串 ConnectionStrings:DefaultConnection");

        // ① 连接工厂 —— Singleton：连接池本身是进程级的，工厂无状态
        services.AddSingleton<IDbConnectionFactory>(new DbConnectionFactory(connectionString));

        // ② SQL 映射加载器 —— Singleton：启动读一次，之后只读
        services.AddSingleton<ISqlLoader>(_ =>
        {
            var xmlPath = Path.Combine(AppContext.BaseDirectory, "Data", "SqlMaps", "SqlMaps.xml");
            if (!File.Exists(xmlPath))
                xmlPath = Path.Combine(Directory.GetCurrentDirectory(), "Data", "SqlMaps", "SqlMaps.xml");
            if (!File.Exists(xmlPath))
                throw new FileNotFoundException("未找到 SqlMaps.xml，请检查 csproj 里的 Content/CopyToOutputDirectory", xmlPath);
            return new SqlLoader(xmlPath);
        });

        // ③ 审计写入器 —— 独立连接，失败只 Warning
        services.AddScoped<IAuditLogWriter>(sp =>
            new AuditLogWriter(connectionString, sp.GetRequiredService<ILogger<AuditLogWriter>>()));

        // ④ 审计装饰器 —— Scoped（依赖 ICurrentUserService / IClientInfoService，都是请求级）
        services.AddScoped<RepositoryAuditService>();

        // ⑤ 多租户 —— Scoped（依赖 HttpContext）
        services.AddScoped<ITenantService, TenantService>();

        // ⑥ 工作单元 —— Scoped（★ 必须是 Scoped，它持有请求级的变更追踪状态）
        services.AddScoped<IUnitOfWork, DapperUnitOfWork>();

        return services;
    }
}
```

> **为什么 `IUnitOfWork` 必须是 Scoped？** 它内部有 `_tracked` 字典。
> 如果是 Singleton，两个并发请求会互相污染变更追踪 —— 结果就是 A 用户改的数据被 B 用户提交。
> 这是 DI 生命周期最容易出事的地方，见 [4.2](#42-常见问题) 第 5 条。

```csharp
using RBS.Application.Common.Interfaces;
using RBS.Application.DTOs.Organization;
using RBS.Core.Entities.Organization;
using RBS.Core.Interfaces.UnitOfWork;
using BCryptNet = BCrypt.Net.BCrypt;

namespace RBS.Application.Services.Organization;

/// <summary>
/// 认证应用服务实现
///
/// 一次登录要查 3 次库：① 按用户名找用户 ② 角色 ③ 权限码
/// 权限码来自 RoleMenus → Menus.PermissionCode（SQL 在 SqlMaps.xml 里）
/// </summary>
public class AuthService : IAuthService
{
    private readonly IUnitOfWork _uow;
    private readonly ITokenService _tokenService;

    public AuthService(IUnitOfWork uow, ITokenService tokenService)
    {
        _uow = uow;
        _tokenService = tokenService;
    }

    public async Task<LoginResponse> LoginAsync(string username, string password, CancellationToken ct = default)
    {
        var user = await _uow.Users.GetByUsernameAsync(username, ct);

        // ★ 三种失败原因合并成同一句提示：不给攻击者「这个用户名存在」的信息
        if (user == null || !user.IsActive || !BCryptNet.Verify(password, user.PasswordHash))
            throw new UnauthorizedAccessException("用户名或密码错误");

        var permissions = await _uow.Users.GetUserPermissionsAsync(user.Id, ct);
        var roles = await _uow.Roles.GetByUserIdAsync(user.Id, ct);

        return new LoginResponse
        {
            Token = _tokenService.GenerateToken(user),
            User = new UserInfo
            {
                Id = user.Id,
                Username = user.Username,
                DisplayName = user.DisplayName,
                Phone = user.Phone,
                Email = user.Email,
                CompanyId = user.CompanyId,
                DefaultCompanyId = user.DefaultCompanyId ?? user.CompanyId,
                IsSuperAdmin = user.IsSuperAdmin,
                Roles = roles.Select(MapRole).ToList()
            },
            Roles = roles.Select(MapRole).ToList(),
            Permissions = permissions
        };
    }

    public async Task<UserProfileDto> GetProfileAsync(Guid userId, CancellationToken ct = default)
    {
        var user = await _uow.Users.GetByIdAsync(userId, ct)
            ?? throw new KeyNotFoundException("用户不存在");

        var permissions = await _uow.Users.GetUserPermissionsAsync(userId, ct);
        var roles = await _uow.Roles.GetByUserIdAsync(userId, ct);

        return new UserProfileDto
        {
            Id = user.Id,
            Username = user.Username,
            DisplayName = user.DisplayName,
            Phone = user.Phone,
            Email = user.Email,
            CompanyId = user.CompanyId,
            DefaultCompanyId = user.DefaultCompanyId ?? user.CompanyId,
            IsSuperAdmin = user.IsSuperAdmin,
            Roles = roles.Select(MapRole).ToList(),
            Permissions = permissions
        };
    }

    private static RoleInfo MapRole(Role r) => new() { Id = r.Id, Name = r.Name, Code = r.Code };
}

### 第 32 步 `src/RBS.Api/Services/CurrentUserService.cs`

```csharp
using System.Security.Claims;
using RBS.Core.Interfaces.Services;

namespace RBS.Api.Services;

/// <summary>
/// 当前用户服务 —— 把 JWT Claims 翻译成 Core 层的 ICurrentUserService
///
/// 为什么放在 Api 层？因为它依赖 HttpContext，而 Core 层不允许依赖 ASP.NET Core。
/// 这就是「接口在 Core、实现在最外层」的典型例子。
/// </summary>
public class CurrentUserService : ICurrentUserService
{
    private readonly IHttpContextAccessor _httpContextAccessor;

    public CurrentUserService(IHttpContextAccessor httpContextAccessor)
        => _httpContextAccessor = httpContextAccessor;

    public Guid UserId
    {
        get
        {
            var claim = _httpContextAccessor.HttpContext?.User?.FindFirst(ClaimTypes.NameIdentifier)?.Value;
            return claim != null && Guid.TryParse(claim, out var id) ? id : Guid.Empty;
        }
    }

    public string? Username
        => _httpContextAccessor.HttpContext?.User?.FindFirst(ClaimTypes.Name)?.Value;

    public bool IsSuperAdmin
    {
        get
        {
            var claim = _httpContextAccessor.HttpContext?.User?.FindFirst("IsSuperAdmin")?.Value;
            return bool.TryParse(claim, out var val) && val;
        }
    }

    public Guid? CompanyId
    {
        get
        {
            var claim = _httpContextAccessor.HttpContext?.User?.FindFirst("CompanyId")?.Value;
            return claim != null && Guid.TryParse(claim, out var id) ? id : null;
        }
    }

    public List<Guid> RoleIds
        => _httpContextAccessor.HttpContext?.User?.FindAll(ClaimTypes.Role)
               .Select(c => Guid.TryParse(c.Value, out var id) ? id : Guid.Empty)
               .Where(id => id != Guid.Empty).ToList() ?? new();

    public List<string> Permissions
        => _httpContextAccessor.HttpContext?.User?.FindAll("Permission")
               .Select(c => c.Value).ToList() ?? new();
}
```

> **`RoleIds` 和 `Permissions` 在这里恒为空**，因为第 33 步的 `TokenService` 没有往 token 里塞这两类 claim。
> 这不是笔误 —— 详细解释见第 33 步下面的说明。

### 第 33 步 `src/RBS.Api/Services/TokenService.cs`

```csharp
using System.IdentityModel.Tokens.Jwt;
using System.Security.Claims;
using System.Text;
using Microsoft.IdentityModel.Tokens;
using RBS.Application.Services.Organization;
using RBS.Core.Entities.Organization;

namespace RBS.Api.Services;

/// <summary>JWT 签发服务 —— 只放「身份」信息，不放权限码</summary>
public class TokenService : ITokenService
{
    private readonly IConfiguration _configuration;

    public TokenService(IConfiguration configuration) => _configuration = configuration;

    public string GenerateToken(User user)
    {
        var jwtSettings = _configuration.GetSection("JwtSettings");
        var secretKey = jwtSettings["SecretKey"] ?? "YourSuperSecretKeyForJwtTokenGenerationAtLeast32Chars!";
        var issuer = jwtSettings["Issuer"] ?? "RBS";
        var audience = jwtSettings["Audience"] ?? "RBS";
        var expirationMinutes = int.Parse(jwtSettings["ExpirationMinutes"] ?? "120");

        var claims = new List<Claim>
        {
            new(ClaimTypes.NameIdentifier, user.Id.ToString()),   // → CurrentUserService.UserId
            new(ClaimTypes.Name, user.Username),                   // → CurrentUserService.Username
            new("DisplayName", user.DisplayName),
            new("IsSuperAdmin", user.IsSuperAdmin.ToString()),     // → TenantService.IsSuperAdmin
            new("CompanyId", user.CompanyId?.ToString() ?? ""),
            new("DefaultCompanyId", user.DefaultCompanyId?.ToString() ?? "")
        };

        var key = new SymmetricSecurityKey(Encoding.UTF8.GetBytes(secretKey));
        var token = new JwtSecurityToken(
            issuer: issuer,
            audience: audience,
            claims: claims,
            expires: DateTime.UtcNow.AddMinutes(expirationMinutes),
            signingCredentials: new SigningCredentials(key, SecurityAlgorithms.HmacSha256));

        return new JwtSecurityTokenHandler().WriteToken(token);
    }
}
```

> **⚠️ 一个必须知道的取舍：** token 里**没有** `Permission` / `Role` claim。
> - 好处：权限改完之后用户**下一次刷新页面就生效**，不用等 token 过期（因为权限是每次登录/`/api/auth/me` 时查库拿的）。
> - 代价：`ICurrentUserService.Permissions` 恒为空数组 —— 后端**无法**用权限码做校验。
>
> 所以本项目的权限码目前是**纯前端显隐**用的（前端文档 §3.6 的 `v-permission`）。
> 这是有意的设计（后端只校验「登录了没有」，不校验「有没有这个权限」），
> 但你必须清楚：**前端隐藏按钮不等于安全边界** —— 用 curl 直接打 `DELETE /api/roomtypes/{id}` 一样能删。
> 想在服务端补上，见 [3.13](#313-扩展服务端权限拦截把显示不显示变成能不能做)。

### 第 34 步 `src/RBS.Api/Middleware/ExceptionLoggingMiddleware.cs`

```csharp
using System.Security.Claims;
using System.Text.Json;
using Dapper;
using RBS.Core.Common;
using RBS.Core.Interfaces.Persistence;

namespace RBS.Api.Middleware;

/// <summary>
/// 全局异常捕获中间件 —— 放在管道最前面，兜住所有下游异常
///
/// 两条规则：
///   ① OperationCanceledException → 499（客户端自己取消了，不算错误，别刷日志）
///   ② 其他异常 → 写 SystemLogs 表 + 返回统一 JSON { code: "SYSTEM_ERROR" }
/// </summary>
public class ExceptionLoggingMiddleware
{
    private readonly RequestDelegate _next;
    private readonly IServiceProvider _serviceProvider;
    private readonly ILogger<ExceptionLoggingMiddleware> _logger;

    public ExceptionLoggingMiddleware(RequestDelegate next, IServiceProvider serviceProvider,
        ILogger<ExceptionLoggingMiddleware> logger)
    {
        _next = next;
        _serviceProvider = serviceProvider;
        _logger = logger;
    }

    public async Task InvokeAsync(HttpContext context)
    {
        try
        {
            await _next(context);
        }
        catch (OperationCanceledException)
        {
            if (!context.Response.HasStarted) context.Response.StatusCode = 499;
        }
        catch (Exception ex)
        {
            _logger.LogError(ex, "HTTP {Method} {Path} 产生未处理异常", context.Request.Method, context.Request.Path);
            await LogExceptionAsync(context, ex);

            context.Response.StatusCode = 500;
            context.Response.ContentType = "application/json; charset=utf-8";
            await context.Response.WriteAsync(JsonSerializer.Serialize(new
            {
                code = "SYSTEM_ERROR",
                message = "系统错误，请稍后重试"
            }));
        }
    }

    /// <summary>
    /// 异常落库 —— 用**独立 DI 作用域 + 独立连接**，
    /// 避免复用正在出错的那个请求的 DbContext/连接（复用可能再次失败）
    /// </summary>
    private async Task LogExceptionAsync(HttpContext context, Exception ex)
    {
        try
        {
            using var scope = _serviceProvider.CreateScope();
            var db = scope.ServiceProvider.GetRequiredService<IDbConnectionFactory>();
            using var conn = db.CreateConnection();
            conn.Open();

            var userIdStr = context.User?.FindFirst(ClaimTypes.NameIdentifier)?.Value;
            Guid? userId = userIdStr != null && Guid.TryParse(userIdStr, out var uid) ? uid : null;

            await conn.ExecuteAsync(@"
                INSERT INTO SystemLogs (Id, Level, Message, Exception, Source, Path, Method, IpAddress, UserAgent, UserId, UserDisplayName, CreatedAt)
                VALUES (@Id, @Level, @Message, @Exception, @Source, @Path, @Method, @IpAddress, @UserAgent, @UserId, @UserDisplayName, @CreatedAt)",
                new
                {
                    Id = Guid.NewGuid(),
                    Level = "Error",
                    Message = ex.Message,
                    Exception = ex.ToString(),
                    Source = ex.Source,
                    Path = context.Request.Path.Value,
                    Method = context.Request.Method,
                    IpAddress = context.Connection.RemoteIpAddress?.ToString(),
                    UserAgent = context.Request.Headers["User-Agent"].ToString(),
                    UserId = userId,
                    UserDisplayName = context.User?.FindFirst("DisplayName")?.Value,
                    CreatedAt = ChinaTime.Now
                });
        }
        catch
        {
            // ★ 记日志失败绝不能盖住原始异常
        }
    }
}
```

> **关于 `ToString()`**：`context.Request.Headers["User-Agent"]` 的类型是 `StringValues`，
> 它重写了 `ToString()`，且**取一个不存在的 header 返回 `StringValues.Empty` 而不是抛异常** ——
> 所以上面那样写既能编译，也不会因为客户端没发 `User-Agent` 而崩。
> 想写得更"类型安全"一点可以用强类型属性 `context.Request.Headers.UserAgent.ToString()`，效果一样。
>
> **这段代码最容易被忽略、却最重要的一行是 `catch { }` 里的注释**：
> 记日志失败（表被锁、列名改了、连接断了）**绝不能把原始异常盖掉**。
> 中间件的职责是"原样把异常传下去 + 尽力留痕"，不是"保证留痕"。

    }

    /// <summary>
    /// GET /api/auth/me —— 取当前用户资料（前端刷新页面后调用）
    /// 响应是**扁平**结构：{ id, username, roles, permissions, ... }
    /// </summary>
    [HttpGet("me")]
    [Authorize]
    public async Task<IActionResult> Me(CancellationToken ct)
    {
        try
        {
            return Ok(await _authService.GetProfileAsync(_currentUser.UserId, ct));
        }
        catch (KeyNotFoundException)
        {
            return Unauthorized();
        }
    }
}
```

> **`[Route("api/[controller]")]` 里的 `[controller]`** = 类名去掉 `Controller` 后缀 → `Auth` → `api/auth`。
> `RoomTypesController` 同理 → `api/roomtypes`（全小写，因为路由不区分大小写）。
> 前端文档 §3.1 写的 `/api/roomtypes` 就是这么来的 —— **不需要手写任何路由配置**。

//   C# 的 Name → 前端拿到的 name；Ignored 的 null 让响应体更干净
builder.Services.AddControllers()
    .AddJsonOptions(options =>
    {
        options.JsonSerializerOptions.PropertyNamingPolicy = System.Text.Json.JsonNamingPolicy.CamelCase;
        options.JsonSerializerOptions.DictionaryKeyPolicy = System.Text.Json.JsonNamingPolicy.CamelCase;
        options.JsonSerializerOptions.DefaultIgnoreCondition =
            System.Text.Json.Serialization.JsonIgnoreCondition.WhenWritingNull;

// ===== ② Swagger =====
builder.Services.AddEndpointsApiExplorer();
builder.Services.AddSwaggerGen();

// ===== ③ JWT 认证 =====
var jwtSettings = builder.Configuration.GetSection("JwtSettings");
var secretKey = jwtSettings["SecretKey"] ?? "YourSuperSecretKeyForJwtTokenGenerationAtLeast32Chars!";

builder.Services.AddAuthentication(options =>
{
    options.DefaultAuthenticateScheme = JwtBearerDefaults.AuthenticationScheme;
    options.DefaultChallengeScheme = JwtBearerDefaults.AuthenticationScheme;
})
.AddJwtBearer(options =>
{

    };
});

// ===== ④ CORS —— 允许前端开发服务器跨域 =====
builder.Services.AddCors(options =>
{
    options.AddPolicy("AllowWebApp", policy =>
        policy.WithOrigins("http://localhost:5173", "http://localhost:5174")
              .AllowAnyHeader()
              .AllowAnyMethod()
              .AllowCredentials());
});

// ===== ⑤ 请求级服务（Api 层特有）=====
// IHttpContextAccessor 是 TenantService / ClientInfoService / CurrentUserService 的地基
builder.Services.AddHttpContextAccessor();
builder.Services.AddScoped<ICurrentUserService, CurrentUserService>();
builder.Services.AddScoped<ITokenService, TokenService>();   // ★ ITokenService 声明在 AuthService.cs 末尾
builder.Services.AddScoped<IClientInfoService, RBS.Infrastructure.Data.Services.ClientInfoService>();

// ===== ⑥ 两个分层入口 =====

var app = builder.Build();

// ===== 中间件管道（★ 顺序敏感，不要随意调换）=====

// 1. 全局异常 —— 必须最前，才能兜住后面所有环节的异常
app.UseMiddleware<RBS.Api.Middleware.ExceptionLoggingMiddleware>();

}

app.UseCors("AllowWebApp");

// 4. 认证 → 授权 —— 顺序不能反（先知道你是谁，再判断你能不能进）

// 5. 路由

```

> **为什么 `ExceptionLoggingMiddleware` 一定要在最前面？**
> 因为管道是「洋葱」：写在最外层的中间件能捕获里面所有环节（包括认证、模型绑定、控制器）抛出的异常。
> 如果放到 `MapControllers()` 后面，异常在进入它之前就已经冒出去了。
>
> **为什么 CORS 必须在认证之前？** 因为跨域预检 `OPTIONS` 请求**不带** `Authorization` 头，
> 如果认证先执行，预检会被 401 拦掉，浏览器根本发不出真正的请求。
>
> **为什么要有 `using RBS.Application.Services.Organization;`？**
> 因为 `ITokenService` 这个接口**没有**单独建文件，它写在 `AuthService.cs` 的**末尾**
> （见第 28 步）—— 这样"认证服务 + 它依赖的 token 服务契约"放在一起，改动时不容易漏。
> 代价就是：谁要用 `ITokenService`，就得 `using` 那个命名空间。
> `TokenService.cs` 里也有这一句，别忘了两处都加。
> （这个 `using` 是**编译报错才会发现**的那类问题 —— 见下面的"第一次编译"。）

## 1.4 精简说明：本案例省掉了什么

本案例是**骨架**，`src/` 是**完整业务系统**。差异集中在下面这些地方 —— 它们的写法规律和本文教的一样，只是数量多。

| 类别 | 本案例 | `src/` 真实情况 |
|---|---|---|
| 项目数 | 4 个（Core / Application / Infrastructure / Api） | 同样 4 个，无差异 |
| 实体 | 3 个（User / Role / RoomType） | 128 个文件：合同、账单、审批、银行、押金、抄表、导入…… |
| 仓储属性 | `IUnitOfWork` 暴露 3 个 | 50+ 个（含 `IContractRepository` 等大量特化仓储） |
| SqlMaps.xml | 3 条 SQL | **2375 行 / 461 条 SQL** |
| 泛型仓储 | 6 个方法，无分页 | 另有 `GetPagedAsync`（LINQ 版直接抛 `NotSupportedException`，提示你走手写 SQL 分页） |
| 工作单元 | 变更追踪 + 提交 + 重试 | 另有 `BeginTransactionAsync`（共享连接+事务）、`ITransaction`/`DapperTransaction`、`ReloadAsync`、提交后**领域事件分发**（`IDomainEventDispatcher`） |
| 审计 | 写 `{表}_Audit` + 版本号 | 另有 `AuditChangedFields`（记录改了哪几个字段）、`AuditFieldConfigLoader`（从 `audit-field-config.json` 读字段中文名）、`IAuditService`（审计查询接口） |
| Dapper 类型处理器 | 无 | `DbConnectionFactory` 静态构造里注册了值对象处理器（`RoomStatus` ↔ 字符串） |
| 中间件 | 异常捕获 | 另有 `ApiLoggingMiddleware` + `ApiLogChannel`（Channel 缓冲 + 后台服务批量写 `ApiLogs`，不阻塞请求） |
| 日志 | `Microsoft.Extensions.Logging` 默认 | **Serilog**（Console + 滚动文件 `logs/rbs-.log`，保留 30 天） |
| 后台任务 | 无 | `SchedulingHostedService` + `JobScheduleGenerator`（定时作业引擎，带并行度和超时配置） |
| PDF / 报表 | 无 | `QuestPDF` + iTextSharp + QRCoder（生成账单 PDF、二维码） |
| 行政区划 | 无 | 高德 API 或桩实现（有 Key 走高德，无 Key 走桩） |
| 认证 | 登录 + 我的资料 | + 改密码、公司切换（`/api/auth/me` 里的 `companyList`） |
| 权限校验 | 只有 `[Authorize]` | 同样只有 `[Authorize]`（**权限码不做服务端校验**，见第 33 步的说明） |

**结论**：你在这份骨架里学到的每一个模式（分层依赖、泛型仓储、变更追踪、审计装饰器、
Fail-Fast 的 SqlLoader），在 `src/` 里都是**同一个写法放大 N 倍**。骨架是「读懂 src/ 的钥匙」。

## 2.2 登录链

> 前端文档 §2.2 那条链路，**右半边**就是这里。以后端视角从 HTTP 请求往下看：

```
前端（5173）                    Vite proxy               后端（5178）
   │                               │                          │
   │  POST /api/auth/login         │                          │
   │  {username:'admin',           │                          │
   │   password:'123456'}          │                          │
   ├──────────────────────────────►│                          │
   │                               ├─────────────────────────►│
   │                               │                          ▼
   │                               │        AuthController.Login(LoginRequest, ct)

   │                               │            ▼
   │                               │        AuthService.LoginAsync(username, password, ct)
   │                               │            │
   │                               │            ├─① _uow.Users.GetByUsernameAsync(username)
   │                               │            │     └─ DapperUserRepository
   │                               │            │         └─ _sql.Get("Identity.Select.User.ByUsername")
   │                               │            │             └─ SELECT * FROM Users WHERE Username=@Username

**4 个关键点**：

1. **`[AllowAnonymous]` 只写在登录接口上**。其他 Controller 类上写 `[Authorize]`，方法上不用再写。
2. **密码哈希是 BCrypt**（`$2b$12$...`）。种子里 admin 的明文是 **`123456`**（⚠️ 不是别处写的 `admin123`，见 [0.1](#01-前置条件)），
   哈希直接写在 `scripts/SeedBase.sql` 里 —— 所以你不需要跑任何"初始化密码"的代码就能登录。
3. **权限码是"每次登录查库汇总"**，不是从 token 里读的。所以你在数据库里改 `RoleMenus` 授权，
   用户刷新页面（触发 `/api/auth/me`）就生效，不用重新登录。
4. **返回体形状必须和前端对齐**：`permissions` 在**顶层**、`roles` **顶层和 user 里各有一份**。
   这不是冗余，是前端 `setUserData` 的兼容写法要求的（前端文档第 7 步有说明）。

   │     └─ conn.Dispose()（using 结束）
   │
   ├─ .Select(MapToDto)   ← 实体 → DTO，把审计字段挡在接口之外
   ▼
return List<RoomTypeDto>
   │
   ▼
Controller: return Ok(result)
   │
   ▼
AddJsonOptions → CamelCase + 忽略 null
[ { "id":"...", "name":"一室一厅", "description":"...", "isActive":true } ]
   │
   ▼
前端 axios 响应拦截器 → res.data 直接就是数组
```

**为什么"实体 → DTO"这一步不能省？**
因为 `RoomType` 继承 `AuditableEntity`，直接返回实体会把 `createdBy`、`createdIp`、`createdHostname`
一起吐给前端 —— 轻则响应体臃肿，重则**泄露内部 IP 和主机名**。DTO 是安全边界。

## 2.4 写库链（新增 / 修改 / 删除三种走向）

> ★ **这一节是本文的核心。** 三个接口，走了三条**完全不同**的持久化路径 ——
> 理解它们，你就理解了这套「Dapper + UnitOfWork + ChangeTracker」的设计意图。

### 走向 A：POST —— 立即 INSERT，`CommitAsync` 是空转

```
POST /api/roomtypes  {name:'阁楼', description:'带天窗'}
   │
   ▼ RoomTypeService.CreateAsync(request, ct)
   │
   ├─ var entity = new RoomType(request.Name);
   │     └─ 构造函数做校验：名称为空 → throw ArgumentException
   │     └─ AuditableEntity 构造：Id = Guid.NewGuid()，CreatedAt = ChinaTime.Now
   │
   ├─ entity.SetDescription(request.Description);
   │
   ├─ await _uow.RoomTypes.AddAsync(entity, ct)
   │     │
   │     ├─ _auditService.PopulateCreatedFields(entity)
   │     │     ├─ CreatedIp       = 127.0.0.1        （IClientInfoService）
   │     │     ├─ CreatedHostname = localhost
   │     │     └─ CreatedBy       = Guid.Empty 时填当前登录用户
   │     │
   │     ├─ 反射收集列（排除 Updated*、排除导航属性）：
   │     │     Id, CreatedBy, CreatedAt, CreatedIp, CreatedHostname, Name, Description, IsActive
   │     │
   │     ├─ INSERT INTO [RoomTypes] (Id,CreatedBy,CreatedAt,CreatedIp,CreatedHostname,Name,Description,IsActive)
   │     │  VALUES (@Id,@CreatedBy,@CreatedAt,@CreatedIp,@CreatedHostname,@Name,@Description,@IsActive)
   │     │
   │     ├─ _auditService.WriteCreateLogAsync("RoomTypes", entity, ct)
   │     │     └─ INSERT INTO [RoomTypes_Audit] (Id,AuditAction,AuditVersionNo,...) 
   │     │        AuditAction='Create', AuditVersionNo=1（独立连接！）
   │     │
   │     └─ _tracker?.Track(entity, "RoomTypes")     ← ★ 注意：这里也登记了
   │
   └─ await _uow.CommitAsync(ct)
         └─ 比对快照：快照就是刚存进去的样子，一个字段都没变 → changes.Count == 0 → return 0
            （一条 SQL 都不发，纯空转）
```

**关键认识**：`AddAsync` 自己就完成了 INSERT，`CommitAsync` 只是收尾（什么也没干）。
所以新增路径**不需要事务** —— 单条 INSERT 本身是原子的。

### 走向 B：PUT —— 领域方法改属性，`CommitAsync` 发差异 UPDATE

```
PUT /api/roomtypes/{id}  {name:'阁楼(改)', isActive:false}
   │
   ▼ RoomTypeService.UpdateAsync(id, request, ct)
   │
   ├─ var entity = await _uow.RoomTypes.GetByIdAsync(id, ct)
   │     │
   │     ├─ SELECT * FROM [RoomTypes] WHERE Id=@Id
   │     └─ _tracker.Track(entity, "RoomTypes")
   │           ├─ 快照：{ Id:..., Name:'阁楼', Description:'带天窗', IsActive:true,
   │           │           CreatedBy:..., CreatedAt:..., ... }
   │           └─ _tracked["RoomTypes"][id] = (entity 引用, 快照)
   │
   ├─ entity.Rename(request.Name)        ← ★ 实体自己校验 + 赋值
   ├─ entity.SetDescription(...)          （request.Description != null 时）
   ├─ request.IsActive == false → entity.Deactivate()
   │
   │     此时 entity.Name 已经是 '阁楼(改)'，但**数据库还没动**
   │     快照里仍然是 '阁楼' —— 差异就藏在"实体对象 vs 快照"之间
   │
   └─ await _uow.CommitAsync(ct)
         │
         ├─ _tracked 有 1 条 → 继续
         ├─ using var conn = ...; using var tx = conn.BeginTransaction();
         │
         ├─ _auditService.PopulateUpdatedFields(entity)
         │     UpdatedBy = 当前用户, UpdatedAt = ChinaTime.Now,
         │     UpdatedIp = 127.0.0.1, UpdatedHostname = localhost
         │
         ├─ now = EntityToDict(entity)      ← 当前全量字段
         ├─ changes = DiffDict(快照, now)   ← ★ 只留变化：
         │     { Name:'阁楼(改)', IsActive:false,
         │       UpdatedBy:..., UpdatedAt:..., UpdatedIp:..., UpdatedHostname:... }
         │
         ├─ UPDATE [RoomTypes] SET [Name]=@Name,[IsActive]=@IsActive,
         │      [UpdatedBy]=@UpdatedBy,[UpdatedAt]=@UpdatedAt,
         │      [UpdatedIp]=@UpdatedIp,[UpdatedHostname]=@UpdatedHostname
         │   WHERE Id=@Id
         │      ← ★ 只有 6 个字段。如果只改了名字，就只有 5 个字段（不含 IsActive）
         │
         ├─ tx.Commit()
         │
         ├─ foreach auditBatch: LogChangesAsync("RoomTypes", id, "Update", now, updatedBy)
         │     └─ AuditVersionNo = MAX+1 = 2   ← 审计表里出现第 2 版
         │
         └─ _tracked.Clear()
```

**为什么不用 `repo.UpdateAsync()`？** 因为它会把**所有**字段都写一遍（`SET Name=..., Description=...,
IsActive=...`），并发下会把别人刚改的字段覆盖回旧值。差异 UPDATE 只写你改过的字段，冲突面小得多。
这是 UoW + ChangeTracker 存在的主要理由。

> 两个都能用：`UpdateAsync` 适合"我手里有一个完整实体，整体覆盖"；
> `GetByIdAsync + 改属性 + CommitAsync` 适合"我从库里读出来改几个字段"。
> 真实 `src/` 里两种写法都有。

### 走向 C：DELETE —— 物理删除 + 删前快照进审计

```
DELETE /api/roomtypes/{id}
   │
   ▼ RoomTypeService.DeleteAsync(id, ct)
   │
   ├─ var entity = await _uow.RoomTypes.GetByIdAsync(id, ct)
   │     └─ 读不到 → throw KeyNotFoundException("房型不存在") → 500（见 4.2 第 8 条）
   │
   ├─ await _uow.RoomTypes.DeleteAsync(entity, ct)
   │     ├─ oldEntity = await GetByIdAsync(id)      ← 再读一次，拿"删除前"的完整快照
   │     ├─ DELETE FROM [RoomTypes] WHERE Id=@Id    ← ★ 物理删除，不是软删除
   │     └─ _auditService.WriteDeleteAsync("RoomTypes", oldEntity, ct)
   │           └─ AuditAction='Delete'，把删除前所有字段完整写进 RoomTypes_Audit
   │
   └─ await _uow.CommitAsync(ct)   → 又空转（没有脏数据）
```

> **物理删除了，数据还能找回来吗？** 能 —— `RoomTypes_Audit` 里那条 `Action='Delete'` 记录
> 含有删除前的全部字段（这正是 `DeleteAsync` 里先 `GetByIdAsync` 再删的原因）。
> 真实 `src/` 对合同、账单这类**业务**数据用的是状态字段软删除（`IsActive=false` / 状态机），
> 房型这种**字典**数据才物理删除。

## 2.5 审计链

> 三条写路径（INSERT / 差异 UPDATE / DELETE）都会触发审计，但**写入时机和连接**是刻意不同的：

```
                    业务表操作                     审计表写入
                ┌──────────────────┐         ┌────────────────────┐
INSERT ────────►│ RoomTypes        │────────►│ RoomTypes_Audit     │ 同步、独立连接
                │ （同一个连接）    │         │ AuditVersionNo=1    │ 失败只 Warning
                └──────────────────┘         └────────────────────┘

UPDATE ────────►┌──────────────────┐
                │ BEGIN TRAN       │
                │ UPDATE RoomTypes │  ← 差异字段
                │ COMMIT           │         ┌────────────────────┐
                └──────────────────┘────────►│ RoomTypes_Audit     │ ★ 事务提交**之后**才写
                                             │ AuditVersionNo=2    │   同步、独立连接
                                             └────────────────────┘

DELETE ────────►┌──────────────────┐
                │ DELETE RoomTypes │────────►┌────────────────────┐
                └──────────────────┘         │ AuditAction='Delete'│
                                             │ 删除前全量快照       │
                                             └────────────────────┘
```

**三个设计决策，都值得记**：

| 决策 | 为什么 |
|---|---|
| 审计用**独立连接**（`new SqlConnection(_connectionString)`） | 业务事务回滚时审计不该跟着回滚；审计表被锁也不该阻塞业务 |
| 审计在**事务提交之后**写 | 业务没成功就别记"改成功了"的假账 |
| 审计写失败**只 `LogWarning`** | 审计是"附带义务"，不能让主业务因为审计表磁盘满而 500 |
| 审计表**不存在就静默跳过**（`IF EXISTS sys.tables`） | 不是每张表都要审计；加一张表不用改代码 |

**审计表怎么建？** `scripts/Init.sql` 里每张业务表都配了 `{表名}_Audit`，
结构 = 5 个审计元数据列 + 业务表全字段（全部可空）。例如 `RoomTypes_Audit`：

```sql
CREATE TABLE [RoomTypes_Audit] (
    [AuditId] BIGINT IDENTITY(1,1) NOT NULL PRIMARY KEY,  -- 自增主键
    [AuditAction] VARCHAR(20) NOT NULL,                    -- Create/Update/Delete
    [AuditVersionNo] INT NOT NULL,                          -- 版本号（第几次变更）
    [AuditChangedAt] DATETIME2 NOT NULL,                    -- 操作时间
    [AuditChangedBy] UNIQUEIDENTIFIER NOT NULL,             -- 操作人
    [AuditChangedHostname] VARCHAR(100),                    -- 操作人主机名
    [Id] UNIQUEIDENTIFIER NOT NULL,                         -- ↓ 以下全是业务字段
    [Name] NVARCHAR(100), [Description] NVARCHAR(500), [IsActive] BIT,
    [CreatedBy] UNIQUEIDENTIFIER, [CreatedAt] DATETIME2, ...
)
```

## 2.6 多租户链

> 一条 `HasCompanyFilter` 判断，决定了「这个查询要不要自动加 `AND CompanyId=@CompanyId`」。

```
                    getAllAsync / getByIdAsync / existsAsync
                                 │
                     HasCompanyFilter(out cid)?
                                 │
        ┌────────────────────────┴────────────────────────┐
        │ ① _tenant == null？                              │ 是 → 不过滤
        │ ② _tenant.EffectiveCompanyId == null？           │ 是 → 不过滤（超管看全部）
        │ ③ typeof(IHasCompany).IsAssignableFrom(T)？      │ 否 → 不过滤
        └────────────────────────┬────────────────────────┘
                                 │ 三条都通过
                                 ▼
              WHERE Id=@Id AND CompanyId=@CompanyId
                                 │
                                 ▼
                    EffectiveCompanyId 怎么来的？
                    ┌──────────────────────────────────────────┐
                    │ IsSuperAdmin == true                     │
                    │   └─ 读 ?companyId=xxx  →  有则用它       │
                    │                           无则 null（全部）│
                    │ IsSuperAdmin == false                    │
                    │   └─ 直接用 token 里的 CompanyId           │
                    │      （普通用户永远无法越权看别家）        │
                    └──────────────────────────────────────────┘
```

**三个实例对照**（都用同一套泛型仓储）：

| 实体 | 实现 IHasCompany？ | 普通用户查询时 | 超管不带 `?companyId` 时 |
|---|---|---|---|
| `RoomType`（房型字典） | ❌ 否 | `SELECT * FROM RoomTypes` | 同左（字典表全局共享） |
| `HousingUnit`（房源） | ✅ 是 | `... WHERE CompanyId=@CompanyId` | `SELECT * FROM HousingUnits`（全部） |
| `Contract`（合同，特化仓储） | ✅ 是 | 同上 | 同上 |

> **这就是"标记接口"的威力**：隔离与否由**实体声明**，不由每个查询手写。
> 新人加实体时，只需要回答一个问题：「这张表的数据按公司隔离吗？」—— 实现 `IHasCompany` 就自动隔离了。
>
> ⚠️ **但要注意它的边界**：泛型仓储的 6 个方法自动过滤，
> 而**特化仓储里手写的 SQL 必须自己加 `WHERE CompanyId=@CompanyId`**（SqlMaps.xml 里能看到）。
> 这也是为什么复杂业务表宁可写特化仓储 —— 隔离条件能显式出现在 SQL 里，一眼可审。

## 3.2 第 1 步：准备数据库

本案例**不重写 DDL** —— 直接用仓库里现成的两个脚本。这是最省事、也最"真"的做法：
本仓库所有表、索引、审计表、种子数据（含 admin 账号和房型菜单权限）都在里面。

```bash
# 在仓库根目录执行（sqlcmd 随 SQL Server 一起装，或用 SSMS 打开这两个文件执行）
sqlcmd -S . -d master -U sa -P 你的密码 -C -i scripts/Init.sql
sqlcmd -S . -d RBS    -U sa -P 你的密码 -C -i scripts/SeedBase.sql
```

> `Init.sql` 会创建 `RBS` 库和 **60+ 张表**（每张业务表都带一张 `_Audit` 审计表）。
> `SeedBase.sql` 会插入公司、角色、菜单、admin 用户和 **10 条房型数据**。
> 两个脚本都是幂等的（`IF NOT EXISTS`），重复执行不会重复插。

**这一步之后你应该能查到 10 条房型**：

```sql
SELECT [Name],[Description],[IsActive] FROM [RoomTypes] ORDER BY [Name];
```

### ⚠️ 这里有一个真实的坑（本案例已实测确认）

`RoomTypes` 表是**别的模块在用**的表，它的列**比 `RoomType` 实体多**。
对一下：

| 列 | `Init.sql` 里的定义 | `RoomType` 实体有对应属性吗？ |
|---|---|---|
| `Id` | `UNIQUEIDENTIFIER NOT NULL` | ✅（基类） |
| `CreatedBy/CreatedAt/CreatedIp/CreatedHostname` | `CreatedBy` **NOT NULL**，其余可空 | ✅（基类） |
| `UpdatedBy/UpdatedAt/UpdatedIp/UpdatedHostname` | 可空 | ✅（基类） |
| `Name` | `NVARCHAR(100) NOT NULL` | ✅ |
| `Description` | `NVARCHAR(500)` 可空 | ✅ |
| `IsActive` | `BIT NOT NULL DEFAULT 1` | ✅ |
| **`Category`** | **`VARCHAR(20) NOT NULL`（无默认值）** | ❌ **没有** |
| **`Code`** | **`VARCHAR(50) NOT NULL`（无默认值）** | ❌ **没有** |
| **`SortOrder`** | `INT NOT NULL DEFAULT 0` | ❌（有默认值，能过） |
| **`CompanyId`** | **`UNIQUEIDENTIFIER NOT NULL`（无默认值）** | ❌ **没有** |

`DapperRepository<RoomType>.AddAsync` 是**反射按实体属性拼 INSERT 的**，于是它生成的是：

```sql
INSERT INTO [RoomTypes] (Id,CreatedBy,CreatedAt,CreatedIp,CreatedHostname,Name,Description,IsActive)
VALUES (@Id,@CreatedBy,@CreatedAt,@CreatedIp,@CreatedHostname,@Name,@Description,@IsActive)
```

`Category`、`Code`、`CompanyId` 三个 NOT NULL 列**没出现在列表里** → 表定义拒绝。
我自己在本地这个库上实测（放在事务里跑完就回滚，没留数据）：

```
Msg 515, Level 16, State 2, Server WIN-0JG8A6B4L3D, Line 1
不能将值 NULL 插入列 'Category'，表 'RBS.dbo.RoomTypes'；列不允许有 Null 值。INSERT 失败。
```

**也就是说：查询没问题（`SELECT *` 多出来的列 Dapper 会忽略），但 `POST /api/roomtypes` 会 500。**
种子里那 10 条数据是 `INSERT` 时**显式指定了** `Category/Code/CompanyId` 的，所以列表页看起来一切正常 ——
这正是这类"列漂移"最难发现的地方。

**两种解法，选一个：**

**方案 A（推荐，改库不改代码）** —— 让这三列可空，并把唯一索引改成筛选索引：

```sql
-- 三个 NOT NULL 列放开（房型模块不从实体写它们，由其它模块维护）
ALTER TABLE [RoomTypes] ALTER COLUMN [Category]  VARCHAR(20)       NULL;
ALTER TABLE [RoomTypes] ALTER COLUMN [Code]      VARCHAR(50)       NULL;
ALTER TABLE [RoomTypes] ALTER COLUMN [CompanyId] UNIQUEIDENTIFIER  NULL;

-- 唯一索引必须改成筛选索引：SQL Server 的唯一索引把多个 NULL 视为重复，
-- 不筛选的话第二条"Code 为空"的记录就插不进去了
DROP INDEX [IX_RoomTypes_Code] ON [RoomTypes];
CREATE UNIQUE INDEX [IX_RoomTypes_Code] ON [RoomTypes]([Code]) WHERE [Code] IS NOT NULL;
```

> 上面 5 条语句我也在这个库上实测过：**同样放在事务里执行 → 再跑那条相同的 INSERT → 成功插入 1 行 → 回滚**，
> 回滚后 `is_nullable` 仍是 0，说明这只是验证、没有改动你的数据库。
> 你确认要用方案 A，就**去掉事务**正式执行一次。

**方案 B（改代码，让实体对齐表）** —— 给实体补上这三列 + 公司隔离：

```csharp
public class RoomType : AuditableEntity, IHasCompany   // ← 加上 IHasCompany，就自动按公司隔离
{
    public string Category { get; private set; } = string.Empty;
    public string Code { get; private set; } = string.Empty;
    public int SortOrder { get; private set; }
    public Guid CompanyId { get; private set; }        // ← IHasCompany 要求的属性
    // …其余不变，构造函数里补上 Category/Code 的赋值和校验
}
```

> 方案 B 更"正确"（实体忠实反映表），但要连带改 DTO、前端表单、种子数据，
> 而且**一旦实现 `IHasCompany`，查询就自动加 `WHERE CompanyId=@CompanyId`** ——
> 普通用户只看得到自己公司的房型，行为会变（可能是你想要的，也可能不是）。
> **它同时是会破坏 `Card` 之外所有历史的改动，学习阶段不建议。**
>
> 📌 **这个"坑"本身就是最好的教材**。它演示了两件事：
> ① 泛型仓储的"反射拼 SQL"是**假设实体覆盖表结构**的 —— 表加了列，实体不跟，新增就会炸，而查询看不出来；
> ② 这正是为什么 `src/` 里**复杂表都写特化仓储 + SqlMaps.xml**（列显式列出，漂移会立刻在编译/评审时暴露），
> 泛型仓储只用在结构简单、和实体一一对应的表上。

## 3.3 第 2 步：Core 实体 `RoomType.cs`

**新建** `src/RBS.Core/Entities/Property/RoomType.cs`

> 这一步在整个第 1 章的**第 11 步**之前做（`IUnitOfWork` 要引用它）。
> 实体是**充血模型**：不是一堆 `{ get; set; }`，而是**私有 setter + 领域方法**。
> 好处是"怎么改才合法"这件事只有实体自己说了算 —— 服务层和服务层以外的代码都不许绕过校验。

```csharp
namespace RBS.Core.Entities.Property;
using RBS.Core.Entities.Base;

/// <summary>
/// 房型字典实体 — 标识房源的类型分类
/// 如 "单间"、"一室一厅"、"两室一厅"、"商铺"、"办公室" 等
/// 用于业务分类统计和定价基准
/// </summary>
public class RoomType : AuditableEntity
{
    /// <summary>房型名称，如 "单间"、"一室一厅"</summary>
    public string Name { get; private set; } = string.Empty;
    /// <summary>房型描述，可选</summary>
    public string? Description { get; private set; }
    /// <summary>是否启用，false 表示已废弃不再使用</summary>
    public bool IsActive { get; private set; } = true;

    /// <summary>仅供反序列化使用（Dapper 走公开构造函数，但保留它不影响）</summary>
    private RoomType() { }

    /// <summary>
    /// 创建房型
    /// </summary>
    /// <param name="name">房型名称，不能为空</param>
    /// <exception cref="ArgumentException">当名称为空时抛出</exception>
    public RoomType(string name)
    {
        if (string.IsNullOrWhiteSpace(name))
            throw new ArgumentException("房型名称不能为空", nameof(name));
        Name = name;
        IsActive = true;
    }

    /// <summary>重命名房型</summary>
    /// <param name="name">新名称，不能为空</param>
    /// <exception cref="ArgumentException">当名称为空时抛出</exception>
    public void Rename(string name)
    {
        if (string.IsNullOrWhiteSpace(name))
            throw new ArgumentException("房型名称不能为空", nameof(name));
        Name = name;
    }
    /// <summary>设置描述信息，null 表示清空</summary>
    public void SetDescription(string? description) => Description = description;
    /// <summary>启用房型</summary>
    public void Activate() => IsActive = true;
    /// <summary>停用房型</summary>
    public void Deactivate() => IsActive = false;
}
```

**三个设计点，每一个都有代价和收益**：

| 设计 | 收益 | 代价 / 注意 |
|---|---|---|
| `private set` | 外面只能通过 `Rename/Deactivate` 改，校验不可能被绕过 | Dapper 写字段时走反射（`属性.SetValue`），**能写 private setter**，不受影响 |
| 构造函数校验 | "名称不能为空"这条规则只有一份（不是 Controller 一份、Service 一份、前端一份） | 抛的是 `ArgumentException`，会被 `ExceptionLoggingMiddleware` 变成 **500**，不是 400（见 3.13） |
| **不实现 `IHasCompany`** | 房型是**全局字典**，所有公司共用一套（十室八厅没必要每家公司各配一份） | 代价是没法按公司定制房型。`HousingUnit`（房源）就实现了它 —— 见 2.6 的对照表 |

## 3.6 第 5 步：Application 服务实现

**新建** `src/RBS.Application/Services/Property/RoomTypeService.cs`

```csharp
using RBS.Application.Common.Interfaces;
using RBS.Application.DTOs.Property;
using RBS.Core.Entities.Property;
using RBS.Core.Interfaces.UnitOfWork;

namespace RBS.Application.Services.Property;

/// <summary>
/// 房型服务。
///
/// ★ 请重点体会三个方法在持久化上的**不同写法**（对应第 2 章的三种走向）：
///   CreateAsync → AddAsync 立即 INSERT，CommitAsync 只是收尾
///   UpdateAsync → GetByIdAsync 拍快照 → 领域方法改属性 → CommitAsync 发差异 UPDATE
///   DeleteAsync → GetByIdAsync → DeleteAsync（含审计）→ CommitAsync 空转
/// </summary>
public class RoomTypeService : IRoomTypeService
{
    private readonly IUnitOfWork _uow;
    public RoomTypeService(IUnitOfWork uow) => _uow = uow;

    public async Task<List<RoomTypeDto>> GetListAsync(CancellationToken ct = default)
    {
        var items = await _uow.RoomTypes.GetAllAsync(ct);
        return items.Select(MapToDto).ToList();
    }

    public async Task<RoomTypeDto?> GetByIdAsync(Guid id, CancellationToken ct = default)
    {
        var entity = await _uow.RoomTypes.GetByIdAsync(id, ct);
        return entity == null ? null : MapToDto(entity);
    }

    public async Task<RoomTypeDto> CreateAsync(CreateRoomTypeRequest request, CancellationToken ct = default)
    {
        // ① 用构造函数创建 —— 校验在实体里，不在服务里
        var entity = new RoomType(request.Name);
        entity.SetDescription(request.Description);

        // ② 立即 INSERT（泛型仓储反射拼 SQL）
        await _uow.RoomTypes.AddAsync(entity, ct);

        // ③ 收尾（新增路径下它不做任何事，见 2.4 走向 A）—— 但别省，语义上这是"提交"
        await _uow.CommitAsync(ct);

        return MapToDto(entity);
    }

    public async Task UpdateAsync(Guid id, UpdateRoomTypeRequest request, CancellationToken ct = default)
    {
        // ① 取 —— GetByIdAsync 内部会 Track（拍快照），这一步是差异 UPDATE 的前提
        var entity = await _uow.RoomTypes.GetByIdAsync(id, ct)
            ?? throw new KeyNotFoundException("房型不存在");

        // ② 改 —— 每个字段都判 null：null = "这一项不动"
        if (request.Name != null) entity.Rename(request.Name);
        if (request.Description != null) entity.SetDescription(request.Description);
        if (request.IsActive.HasValue)
        {
            if (request.IsActive.Value) entity.Activate();
            else entity.Deactivate();
        }

        // ③ 提交 —— CommitAsync 比对快照，只 UPDATE 变了的字段
        await _uow.CommitAsync(ct);
    }

    public async Task DeleteAsync(Guid id, CancellationToken ct = default)
    {
        var entity = await _uow.RoomTypes.GetByIdAsync(id, ct)
            ?? throw new KeyNotFoundException("房型不存在");

        // DeleteAsync 内部会再读一次，把"删除前"的完整快照写进 RoomTypes_Audit
        await _uow.RoomTypes.DeleteAsync(entity, ct);
        await _uow.CommitAsync(ct);
    }

    /// <summary>实体 → DTO。**这是唯一的转换出口**，别在控制器里再写一遍</summary>
    private static RoomTypeDto MapToDto(RoomType r) => new()
    {
        Id = r.Id,
        Name = r.Name,
        Description = r.Description,
        IsActive = r.IsActive
    };
}
```

**这段代码里藏着本框架最重要的三个习惯**：

1. **服务层不认识 HTTP**。没有 `HttpContext`、没有 `IActionResult`、没有 `try/catch` 转状态码。
   它只做"编排"：取实体 → 调领域方法 → 提交。所以它**可以脱离 Web 被单测**。
2. **`ct` 一路往下传**。客户端的连接断了，`CancellationToken` 会取消 Dapper 的查询 ——
   长查询不会白跑。**每一个 `async` 方法都要接 `ct` 并传下去**，这是全仓库的硬约定。
3. **`_uow` 是 `Scoped` 的**，一次请求一个实例，所以"取实体时的快照"和"提交时的差异"是同一份 ——
   这正是变更追踪能工作的前提。

| 代码 | 为什么这么写 |
|---|---|

## 3.9 第 8 步：权限码与菜单数据

前端的 `v-permission="'system:roomtypecreate'"` 能不能命中，取决于**数据库里有没有这个权限码**。
好消息：`scripts/SeedBase.sql` 里**已经种好了**，你第 1 步跑完就有了。这里要做的只是**核对**。

**① 四个权限码挂在菜单表上**（`Menus.PermissionCode`）：

```sql
-- SeedBase.sql 里的原文（节选）
INSERT INTO [Menus] ([Id],[Name],[PermissionCode],[Path],[Icon],[ParentId],[SortOrder],[IsActive],...)
VALUES (@M_System_RoomType,N'房型管理','system:roomtype','/system/roomtypes','Grid',@M_System,9,1,...);
--                                                                 ↑ 菜单：有 Path，无 ParentId 之外的层级
INSERT INTO [Menus] ([Id],[Name],[PermissionCode],[ParentId],[SortOrder],[IsActive],...)
VALUES (@M_System_RoomTypeCreate,N'新增房型','system:roomtypecreate',@M_System_RoomType,10,1,...);
INSERT INTO [Menus] ([Id],[Name],[PermissionCode],[ParentId],...)
VALUES (@M_System_RoomTypeEdit,  N'编辑房型','system:roomtypeedit',  @M_System_RoomType,11,1,...);
INSERT INTO [Menus] ([Id],[Name],[PermissionCode],[ParentId],...)
VALUES (@M_System_RoomTypeDelete,N'删除房型','system:roomtypedelete',@M_System_RoomType,12,1,...);
```

> 注意结构：**一个"菜单"（有 `Path`）+ 三个"按钮/子项"（无 `Path`，`ParentId` 指向菜单）**。
> 三种权限码都进 `Menus` 表同一个列 —— 因为"前端要不要显示这个按钮"和"要不要显示这个菜单"
> 对后端来说是同一件事：**这个用户有没有这个权限码**。

**② 角色 → 菜单的授权**（`RoleMenus`）：

```sql
-- Admin 角色拿到全部启用的菜单（SeedBase.sql 里的原文）
INSERT INTO [RoleMenus] ([Id],[RoleId],[MenuId],[CreatedBy],[CreatedAt])
SELECT NEWID(), @AdminRoleId, M.[Id], @SysUserId, @Now
FROM [Menus] M
WHERE M.[IsActive] = 1
  AND NOT EXISTS (SELECT 1 FROM [RoleMenus] RM WHERE RM.[RoleId] = @AdminRoleId AND RM.[MenuId] = M.[Id]);
```

> 所以 `admin` 用户**自动拥有**这四个权限码，前端按钮会全部显示。

**③ 核对 SQL（跑一下，必须各返回一行）**：

```sql
-- ① 四个权限码都在，且"房型管理"菜单路径正确
SELECT m.[PermissionCode], m.[Path], p.[PermissionCode] AS ParentCode
FROM [Menus] m LEFT JOIN [Menus] p ON p.[Id] = m.[ParentId]
WHERE m.[PermissionCode] IN ('system:roomtype','system:roomtypecreate',
                             'system:roomtypeedit','system:roomtypedelete');

-- ② admin 用户实际能解析出这些权限码（这就是登录接口返回的 permissions）
SELECT DISTINCT m.[PermissionCode]
FROM [RoleMenus] rm
JOIN [Menus] m      ON m.[Id]  = rm.[MenuId]
JOIN [UserRoles] ur ON ur.[RoleId] = rm.[RoleId]
JOIN [Users] u      ON u.[Id]  = ur.[UserId]
WHERE u.[Username] = 'admin' AND m.[PermissionCode] LIKE 'system:roomtype%';
```

预期：

```
PermissionCode              Path                  ParentCode
system:roomtype             /system/roomtypes     NULL          ← 菜单
system:roomtypecreate       NULL                  system:roomtype
system:roomtypeedit         NULL                  system:roomtype
system:roomtypedelete       NULL                  system:roomtype
```

> **`/system/roomtypes` 必须一字不差** —— 前端路由 `path` 就是这么写的（前端文档 §3.4）。
> 但它**只是数据**：本仓库里没有"后端下发生成前端路由"的机制，
> 前端路由是**手写**的 `routes`，菜单接口只是决定**显示不显示**。
> （很多管理框架会拿这个 `Path` 动态生成路由，本仓库不是，见 4.1 第 7 条。）

## 3.11 扩展：分页接口（对接前端 §3.8）

前端文档 §3.8 讲了"接口是分页的怎么写"，但当时后端**没有**分页接口。
现在补上。**注意：绝不改 `GET /api/roomtypes` 的行为**（前端 §3.1 契约是数组），
而是**新增**一个 `/paged` 端点。

分页查询要 `COUNT + OFFSET/FETCH` 两条 SQL —— **这超出了泛型仓储的能力范围**，
正确做法是**特化仓储 + SqlMaps.xml**（这正是本仓库处理复杂查询的标准姿势）。

**① 加两条 SQL** —— `src/RBS.Infrastructure/Data/SqlMaps/SqlMaps.xml`：

```xml
<!-- 房型分页：总数 -->
<select id="Property.Select.RoomTypes.PagedCount">
  SELECT COUNT(1) FROM [RoomTypes] WHERE (@IsActive IS NULL OR [IsActive] = @IsActive)
</select>

<!-- 房型分页：当页数据（SQL Server 2012+ 的 OFFSET/FETCH 语法） -->
<select id="Property.Select.RoomTypes.PagedList">
  SELECT * FROM [RoomTypes]
  WHERE (@IsActive IS NULL OR [IsActive] = @IsActive)
  ORDER BY [CreatedAt] DESC, [Id]
  OFFSET @Offset ROWS FETCH NEXT @PageSize ROWS ONLY
</select>
```

> **`ORDER BY` 在分页里不是可选的** —— `OFFSET/FETCH` 语法强制要求它，否则报错。
> 而且排序必须**稳定**（末尾再加 `[Id]`），否则同一个"第 2 页"两次请求可能返回不同行、漏掉或重复数据。
> **`@IsActive IS NULL OR ...` 是"可选条件"的惯用写法**：不传就是查全部。

**② 特化仓储接口** —— 新建 `src/RBS.Core/Interfaces/Repositories/IRoomTypeRepository.cs`：

```csharp
using RBS.Core.Entities.Property;

namespace RBS.Core.Interfaces.Repositories;

/// <summary>房型仓储 —— 通用 CRUD 用基类，分页这种复杂查询自己加</summary>
public interface IRoomTypeRepository : IRepository<RoomType>
{
    /// <summary>分页查询（page 从 1 开始）</summary>
    Task<PagedResult<RoomType>> GetPagedAsync(int page, int pageSize, bool? isActive,
                                               CancellationToken ct = default);
}
```

**③ 实现** —— 新建 `src/RBS.Infrastructure/Data/Repositories/DapperRoomTypeRepository.cs`：

```csharp
using Dapper;
using RBS.Core.Entities.Property;
using RBS.Core.Interfaces.Persistence;
using RBS.Core.Interfaces.Repositories;
using RBS.Core.Interfaces.Services;

namespace RBS.Infrastructure.Data.Repositories;

/// <summary>
/// 房型仓储实现。
/// ★ 注意命名：跟 DapperUserRepository 一样，**继承泛型仓储拿到 CRUD，
///   只重写/新增自己需要的那一个方法** —— 这就是特化仓储的成本上限。
/// </summary>
public class DapperRoomTypeRepository : DapperRepository<RoomType>, IRoomTypeRepository
{
    private readonly ISqlLoader _sql;
    private readonly IDbConnectionFactory _db;

    public DapperRoomTypeRepository(IDbConnectionFactory db, IAuditLogWriter auditWriter,
        ISqlLoader sql, ITenantService? tenant = null, IChangeTracker? tracker = null)
        : base(db, auditWriter, tracker, tenant)
    {
        _db = db;
        _sql = sql;
    }

    public async Task<PagedResult<RoomType>> GetPagedAsync(int page, int pageSize, bool? isActive,
                                                          CancellationToken ct = default)
    {
        // 入参收口：把非法值挡在这里，别让它们进数据库
        if (page < 1) page = 1;
        if (pageSize < 1) pageSize = 20;
        if (pageSize > 200) pageSize = 200;        // ★ 上限，防止 ?pageSize=999999 打垮数据库

        using var conn = _db.CreateConnection();
        conn.Open();

        var total = await conn.ExecuteScalarAsync<int>(new CommandDefinition(
            _sql.Get("Property.Select.RoomTypes.PagedCount"),
            new { IsActive = isActive }, cancellationToken: ct));

        var items = (await conn.QueryAsync<RoomType>(new CommandDefinition(
            _sql.Get("Property.Select.RoomTypes.PagedList"),
            new { IsActive = isActive, Offset = (page - 1) * pageSize, PageSize = pageSize },
            cancellationToken: ct))).ToList();

        return new PagedResult<RoomType>
        {
            Items = items,
            Total = total,
            Page = page,
            PageSize = pageSize,
            // ★ 向上取整：(total + pageSize - 1) / pageSize
            TotalPages = (int)Math.Ceiling(total / (double)pageSize)
        };
    }
}
```

**④ 让 UoW 用它** —— `DapperUnitOfWork.cs` 里把那一行换成特化的：

```csharp
// 原来（泛型）：
public IRepository<RoomType> RoomTypes => _roomTypes ??= new DapperRepository<RoomType>(_db, _auditWriter, tracker: this, tenant: _tenant);
// 改成（特化，接口仍是 IRepository<RoomType>，调用方无需改）：
public IRoomTypeRepository RoomTypes => _roomTypes ??= new DapperRoomTypeRepository(_db, _auditWriter, _sqlLoader, _tenant, this);
private IRoomTypeRepository? _roomTypes;
```

> ★ **这一步是"零成本升级"的示范**：接口从 `IRepository<RoomType>` 收窄成 `IRoomTypeRepository`，
> 后者**继承前者**，所以 `GetAllAsync`/`AddAsync` 的调用方一行都不用改，
> 而新增的 `GetPagedAsync` 只有分页接口用得到。**特化仓储 = 泛型仓储 + 你要的那几个方法。**

**⑤ 服务 + 控制器**：

```csharp
// IRoomTypeService / RoomTypeService 里加：
Task<PagedResult<RoomTypeDto>> GetPagedAsync(int page, int pageSize, bool? isActive, CancellationToken ct = default);

public async Task<PagedResult<RoomTypeDto>> GetPagedAsync(int page, int pageSize, bool? isActive, CancellationToken ct = default)
{
    var paged = await _uow.RoomTypes.GetPagedAsync(page, pageSize, isActive, ct);
    return new PagedResult<RoomTypeDto>
    {
        Items = paged.Items.Select(MapToDto).ToList(),
        Total = paged.Total, Page = paged.Page,
        PageSize = paged.PageSize, TotalPages = paged.TotalPages

}

// RoomTypesController 里加：

[HttpGet("paged")]

                                         [FromQuery] bool? isActive = null, CancellationToken ct = default)

```

**⑥ 前端的调用**（补进 `web/src/api/roomType.js`）：

响应形状就是前端文档 §3.8 里那个信封（`PagedResult<T>` 的字段名刚好对得上）：

```json

```

> ⚠️ **路由顺序提醒**：`[HttpGet("paged")]` 和 `[HttpGet("{id}")]`（3.12 要加的）同时存在时，
> ASP.NET Core 的路由匹配**不会**把 `paged` 当成 `{id}` —— 它按"字面量优先于参数"匹配。
> 但如果你写成 `[HttpGet("{id:guid}")]` 之外的宽松约束，就要留心了。
> **加 `:guid` 约束是最省心的写法**：`[HttpGet("{id:guid}")]`，让 `paged` 根本不可能匹配到 id 路由。

## 3.12 扩展：详情接口（对接前端 §3.9）

**5 行代码，闭合两文档之间唯一的缺口。** 在 `RoomTypesController` 里加：

```csharp
/// <summary>GET /api/roomtypes/{id} —— 前端详情页（前端文档 §3.9）</summary>

public async Task<IActionResult> Get(Guid id, CancellationToken ct)
{
    var dto = await _service.GetByIdAsync(id, ct);
    return dto == null ? NotFound() : Ok(dto);
}

三点说明：

1. **`{id:guid}` 的路由约束**：只有合法 GUID 才匹配。传一个乱字符串 → `404`（而不是进方法后
   模型绑定失败报 400）。这样 `paged` 之类的新端点永远不会被误认为 id。
2. **查不到返回 `404`，不抛异常**。这是有意的：**"没找到"是正常业务结果，不是错误**。

   （更讲究的做法是定义 `NotFoundException` 并在中间件里映射成 404，见 3.13。）
3. **前端侧不用再打补丁了** —— 前端文档 §3.9 那段"控制器暂未暴露，临时这样写"的注释和

## 3.13 扩展：服务端权限拦截（把"显示不显示"变成"能不能做"）

> ⚠️ **这一节请务必读完再决定做不做。** 它讲的不是"加个功能"，而是**一个安全边界**。

**现状（本仓库真实情况）**：控制器的权限控制只有 `[Authorize]` —— **只校验"登录了没"，
不校验"有没有这个权限"**。四个权限码（`system:roomtypecreate` 等）**只在前端用来隐藏按钮**。

这意味着：**任何人只要登录了，用 Postman 直接打 `POST /api/roomtypes` 就能成功** ——
哪怕前端没给他显示"新增"按钮。

> 前端文档里那句话在这里必须再说一遍：
> **前端隐藏按钮是"用户体验"，不是"安全边界"。** 安全边界只能在服务端。

**加上服务端校验，三种做法，从松到紧**：

**做法 1：控制器上手写（最直观，适合只有一两个接口要管）**

```csharp
[HttpPost]
public async Task<IActionResult> Create([FromBody] CreateRoomTypeRequest request, CancellationToken ct)
{
    if (!User.HasClaim("Permission", "system:roomtypecreate"))   // ⚠️ 见下方说明
        return Forbid();

    var result = await _service.CreateAsync(request, ct);
    return Ok(result);
}
```

> ⚠️ **这段伪代码跑不通，因为它暴露了本框架的一个真实限制**：
> `TokenService` 签发 JWT 时**没有把权限码写进 token**（见第 33 步的 ⚠️ 说明），
> 所以 `User.HasClaim("Permission", ...)` 永远是 false。
> 要么走做法 2（查库），要么先改 `TokenService` 把权限码塞进 Claim。

**做法 2：授权策略 + 查库（推荐，能立刻用）**

```csharp
// Program.cs 里注册一个"按权限码查库"的授权策略提供者
builder.Services.AddSingleton<IAuthorizationHandler, PermissionHandler>();

// 新增 src/RBS.Api/Authorization/PermissionHandler.cs —— 核心就这几行
public class PermissionHandler : AuthorizationHandler<PermissionRequirement>
{
    private readonly IServiceScopeFactory _scopes;   // ★ 授权器是 Singleton，不能用 Scoped 依赖
    public PermissionHandler(IServiceScopeFactory scopes) => _scopes = scopes;

    protected override async Task HandleRequirementAsync(
        AuthorizationHandlerContext context, PermissionRequirement requirement)
    {
        var userId = context.User.FindFirst(ClaimTypes.NameIdentifier)?.Value;
        if (userId == null) return;                       // 没登录 → 不满足（会 401/403）

        using var scope = _scopes.CreateScope();          // ★ 每次开一个作用域拿 UoW
        var uow = scope.ServiceProvider.GetRequiredService<IUnitOfWork>();
        var permissions = await uow.Users.GetUserPermissionsAsync(Guid.Parse(userId));

        if (permissions.Contains(requirement.PermissionCode))
            context.Succeed(requirement);                 // ★ 满足 → 放行
    }
}

// 然后用起来：
[HttpPost]
[Authorize(Policy = "system:roomtypecreate")]
public async Task<IActionResult> Create(...) { ... }
```

**做法 3：过滤器/中间件统一拦截（最省事，但耦合最重）**

```csharp
// 自定义一个 [HasPermission("system:roomtypedelete")] 特性，做一个 IAsyncAuthorizationFilter
// 好处：控制器上一行注解搞定；坏处：要自己处理"查库失败怎么办"这类边界
```

**选哪个？** 学习阶段：

| 场景 | 建议 |
|---|---|
| 只是想把前后端跑通、理解链路 | **先不做**。知道"现在的 `[Authorize]` 只管登录"这件事**已经很重要了** |
| 想让权限真正生效、又不想改 token 结构 | **做法 2**（策略 + 查库）。缓存一下权限码（内存缓存 5 分钟）就不会每请求查库 |
| 想少写代码 | 做法 3 |

> **无论选哪个，`ExceptionLoggingMiddleware` 里都建议顺手加两个映射**，把业务异常翻译成正确的状态码：
>
> ```csharp
> // 在 catch 链里，NotFound 之前
> catch (KeyNotFoundException ex)   { context.Response.StatusCode = StatusCodes.Status404NotFound; }
> catch (UnauthorizedAccessException ex) { context.Response.StatusCode = StatusCodes.Status401Unauthorized; }
> catch (ArgumentException ex)       { context.Response.StatusCode = StatusCodes.Status400BadRequest; }
> ```
>
> 现在它们全都变成 500 —— 这就是 3.10 验证清单第 10 条"不存在的 id 返回 500"的原因，
> 也是 4.2 第 8 条的内容。**知道这个"不完美"在哪、怎么改，比假装它不存在有用。**

## 4.1 加一个业务模块的固定 7 步

> 房型模块已经替你走过一遍。以后加任何模块（比如"收费项目"），**照这 7 步抄**。
> 每步都给出"以房型为例"的具体位置，以及最容易写错的地方。

| 步 | 动作 | 房型的对应物 | 最容易写错的地方 |
|---|---|---|---|
| 1 | **建表 + 建审计表**（照 `Init.sql` 风格） | `RoomTypes` / `RoomTypes_Audit` | 忘了 `_Audit` 表；审计表业务字段要**全部可空** |
| 2 | **Core：实体**（充血模型，私有 setter） | `Entities/Property/RoomType.cs` | 写成 `{ get; set; }`；校验写在 Service 里 |
| 3 | **Application：DTO**（Dto / CreateRequest / UpdateRequest） | `DTOs/Property/RoomTypeDto.cs` | Update 的字段忘了可空 → 前端"不传就是清空" |
| 4 | **Application：服务接口 + 实现** | `IRoomTypeService` / `RoomTypeService` | 忘了把 `ct` 传下去；在 Service 里处理 HTTP 状态码 |
| 5 | **注册服务**（`AddApplicationLayer` 加一行） | `services.AddScoped<IRoomTypeService, RoomTypeService>()` | 用 `AddSingleton` → 跨请求串数据 |
| 6 | **UoW 暴露仓储**（若是新表要特化查询，才加特化仓储） | `IUnitOfWork.RoomTypes` | 忘了在 `DapperUnitOfWork` 里实现（接口加了、实现没加 → 编译不过，还好） |
| 7 | **Api：控制器**（`[ApiController]` + `[Route]` + `[Authorize]`） | `RoomTypesController` | 路由大小写、`[FromQuery]`/`[FromBody]` 标错、忘了 `ct` |

**规律**：**1 → 2 → 3 → 4 → 5 → 6 → 7 的顺序，每一步都只依赖前面已经存在的东西**，
所以任何时刻停下来，解决方案都是编译通过的。这就是"分层 + 依赖倒置"最实用的好处。

> **什么时候需要"特化仓储"？** 出现下面任一情况时：
> ① 需要分页 / 复杂 JOIN / 聚合（泛型仓储做不了，见 3.11）；
> ② 需要绕过自动租户过滤（`IgnoreQueryFilters` 那类语义）；
> ③ 表的列和实体不是一一对应（SQL 显式列清单比反射拼更安全）。
> 其余情况**一律用泛型仓储**，别为了一张简单表写一堆样板代码。

## 4.2 常见问题

**1）所有接口都返回 401，连登录接口也是**

三个最常见原因，按顺序查：

| 原因 | 怎么确认 |
|---|---|
| `appsettings.json` 里 `JwtSettings:SecretKey` 前后不一致（或改了 key 但旧 token 还在用） | 重启后端 + 前端清 `localStorage` 重新登录 |
| `ValidateIssuer`/`ValidateAudience` 为 true，但 token 里的 `iss`/`aud` 不是 `RBS` | 看第 33 步 `TokenService` 和 `Program.cs` 是否都是 `"RBS"` |
| **服务器时钟偏差** | 本案例 `ClockSkew = TimeSpan.Zero`（零容忍），时间差超过几秒就可能被判过期。生产环境可设 `TimeSpan.FromMinutes(1)` |

**2）浏览器报 CORS：`No 'Access-Control-Allow-Origin' header`**

- 前端的**实际源**（协议+主机+端口）必须在 `AllowWebApp` 的白名单里。
  注意 `http://localhost:5173` 和 `http://127.0.0.1:5173` **是两个不同的源**。
- **中间件的顺序错了也会这样**：`UseCors` 必须在 `UseAuthentication` **之前**，
  否则预检请求（`OPTIONS`）会被认证拦掉、根本走不到 CORS。见第 36 步的说明。
- 用 Vite 代理时（前端文档的做法）浏览器看到的是**同源**，不会触发 CORS —— 所以
  "代理下正常、直连报错"是正常的，别去改后端。

**3）启动报 `未找到 SqlMaps.xml`**

`RBS.Infrastructure.csproj` 里的 `<Content>` 那段没了（第 12 步）：
`CopyToOutputDirectory=PreserveNewest` 才会把它复制到 `bin/`。
注意路径用**反斜杠** `Data\SqlMaps\SqlMaps.xml`（MSBuild 里这是惯例）。

**4）启动报 `id "xxx" 不符合命名规范`**

`SqlLoader` 的 Fail-Fast 校验（第 15 步）：id 必须是**四段**
`{模块}.{CRUD}.{实体}.{描述}`，且第二段只能是 `Select/Insert/Update/Delete`。
**这是故意的** —— 宁可启动就崩，也不要运行时才发现某条 SQL 找不到。

**5）`SELECT` 报 `Invalid object name 'Companys'`（表名推断错了）**

`InferTableName` 是**朴素复数化**：`y` → `ies`（`Category` → `Categories`）、
`s/ch/sh/x` → `es`、其余 `+s`。所以 `Company` → `Companys` ❌（正确是 `Companies`）。

三种解法，按推荐度：
① **给实体加 `[Table("Companies")]`**（如果你的实体基类支持 Table 特性）；
② **写特化仓储**，SQL 里显式写表名（最稳，`src/` 的做法）；
③ 改 `InferTableName` 的规则（**最不推荐**：全局影响，容易踩到新的特例）。

> **自查方法**：实体建好后立刻跑一次 `GET` 列表，表名不对会**立刻**报错，不会静默出错。

**6）`GET` 正常，`POST` 报 `不能将值 NULL 插入列 'Xxx'`**

**表有 NOT NULL 列，实体没覆盖到** —— 就是 3.2 那个坑，`RoomTypes.Category` 是活例子。
泛型仓储只能写它"看得见"的列。**解法见 3.2 的方案 A / B。**

**7）`PUT` 返回 204，但数据库里没变**

四种可能：

| 原因 | 症状 | 修 |
|---|---|---|
| **忘了 `await _uow.CommitAsync(ct)`** | `GetByIdAsync` 拍过快照，改完没提交 | 补上（这是最容易犯的） |
| 直接用 DTO/局部变量改了值，没调实体方法 | 改的是 DTO，实体没动，快照自然没差异 | 改实体属性 |
| 改的是**导航属性**（`IsNavProp` 为 true） | 被 `DiffDict` 排除了 | 导航属性不走差异追踪，单独处理 |
| 改的字段**值没变** | 差异为空，一条 SQL 都不发（**这是正常的**） | 无需修 |

**8）找不到 id 时返回 500，而不是 404**

`KeyNotFoundException` 没有在 `ExceptionLoggingMiddleware` 里被专门映射，落到了兜底的 500。
这是 `src/` 的真实行为。想改？见 3.13 结尾那段 catch 映射。

**9）时间差 8 小时**

`ChinaTime.Now` 是 `TimeZoneInfo("China Standard Time")` + `UtcNow`。如果服务器时区不是东八区、
或者你直接用了 `DateTime.Now`，就会出现差 8 小时。
**另一处容易踩**：`Init.sql` 里 `CreatedAt` 的默认值是 `DATEADD(HOUR, 8, GETUTCDATE())` ——
建表默认值和应用写入走的是两条路，如果两者不一致，会出现"种子数据"和"新建数据"时间对不齐。
本案例统一用 C# 侧传入 `CreatedAt`，就是为了一致。

**10）响应里某些字段"消失"了**

`DefaultIgnoreCondition = WhenWritingNull` —— **值为 null 的字段不会出现在 JSON 里**。
前端如果直接读 `list[0].description` 拿到 `undefined`，给个默认值即可（`?? ''`）。
这是**故意的**：响应体更小，也让"没传"和"传了 null"在前端能区分开。

**11）前端登录成功但按钮全都不显示**

权限码链路的**四环**缺一不可，逐环查（用 3.9 的核对 SQL）：

```
Users ──UserRoles──► Roles ──RoleMenus──► Menus ──► PermissionCode
  ↑ 用户有角色吗？        ↑ 角色授过菜单吗？   ↑ 菜单上有码吗？   ↑ 码字符串和前端一致吗？
```

最常见的两环：**新加的用户没分配角色**（`UserRoles` 空）、
**新加的权限码只在 `Menus` 里插了、没在 `RoleMenus` 里授权给任何角色**。

**12）`GetPagedAsync` 报 `NotSupportedException("Dapper 不支持 LINQ 表达式分页")`**

这是**故意的**。泛型仓储**不提供** LINQ 分页 —— 手写 SQL 的架构下，
把 `Expression<Func<T,bool>>` 翻译成 SQL 等于重造 EF Core。
**分页请走特化仓储 + SqlMaps.xml**（3.11 有完整实现）。

**13）数据库连接偶尔超时 / 报"连接池已满"**

`Max Pool Size=100; Min Pool Size=10`（连接串里）。两种情况：
① **`Scoped` 注册写成了 `Singleton`** → 连接被跨请求长期持有，池很快耗尽；
② 有长事务把连接占住了（大报表、批量导入）。
排查：`SELECT ... FROM sys.dm_exec_sessions` 看连接数。

**14）`dotnet run` 报端口被占用**

改 `Properties/launchSettings.json` 里的 `applicationUrl`（**不要改代码**），
然后同步改前端的 Vite 代理目标（`vite.config.js` 的 `proxy['/api'].target`）。

## 4.3 编码约定清单（贴在手边）

| 事项 | 约定 | 反例 |
|---|---|---|
| 异步方法 | 一律 `async Task<T>`，**参数带 `CancellationToken ct = default`** | `async void`；不传 `ct` |
| 服务注册 | 碰数据库的一律 `AddScoped` | `AddSingleton<IUnitOfWork>` ❌ |
| 超时/取消 | `ct` 从控制器一路传到 Dapper 的 `CommandDefinition` | 中间某一层没接 |
| 状态码 | 控制器决定（`Ok`/`NoContent`/`NotFound`），Service **不碰 HTTP** | Service 返回 `IActionResult` |
| 出参 | 一律返回 **DTO**，绝不返回实体 | `return Ok(roomTypeEntity)` ❌ |
| 校验 | 在**实体**里（构造函数 + 领域方法），不在 Controller | Controller 里 `if (name == "")` |
| 写库 | `AddAsync` 立即写；改属性走 `GetByIdAsync` + `CommitAsync` | 忘了 `CommitAsync` |
| SQL | 手写 SQL 只放 `SqlMaps.xml`，**代码里不出现字符串 SQL** | `conn.Query("SELECT ...")` ❌ |
| 审计 | 表命名 `{业务表}_Audit`；失败只 `LogWarning`，不抛 | 让审计失败把业务搞崩 |
| 多租户 | 要按公司隔离的实体实现 `IHasCompany` | 特化仓储手写 SQL 忘了带 `CompanyId` |
| 时间 | 一律 `ChinaTime.Now` | `DateTime.Now` ❌ |
| JSON | 全局 camelCase（`AddJsonOptions`），不要在 DTO 上加 `[JsonPropertyName]` | 逐个字段标注 |

```sql
-- 表存在吗？列对不对？有没有漂移？
SELECT c.[name], t.[name] AS type, c.[max_length], c.[is_nullable]

-- 某条记录的完整变更史
SELECT [AuditVersionNo],[AuditAction],[AuditChangedAt],[AuditChangedBy],[Name],[IsActive]

-- admin 实际拥有的全部权限码（= 登录接口返回的 permissions）
SELECT DISTINCT m.[PermissionCode]
FROM [RoleMenus] rm
JOIN [Menus] m ON m.[Id] = rm.[MenuId]
JOIN [UserRoles] ur ON ur.[RoleId] = rm.[RoleId]
JOIN [Users] u ON u.[Id] = ur.[UserId]
WHERE u.[Username] = 'admin' AND m.[PermissionCode] IS NOT NULL
ORDER BY m.[PermissionCode];
```

**JWT 排错**：把 token 粘到 `https://jwt.io`（**注意：只贴你自己的开发 token，
别把生产的贴进任何在线工具**）。重点看 `exp`、`iss`、`aud` 和 claim 名字。
本框架的 claim 是：`NameIdentifier`、`Name`、`DisplayName`、`IsSuperAdmin`、`CompanyId`、`DefaultCompanyId`
—— **没有** `Permission`、**没有** `Role`。

## B.5 SqlMaps.xml 的命名规范（照抄，别自创）

```xml
<!-- 四段：{模块}.{CRUD}.{实体}.{描述}；CRUD 只能是 Select/Insert/Update/Delete -->
<select id="Property.Select.RoomTypes.PagedList">…</select>
<insert id="Property.Insert.RoomTypes.One">…</insert>
<update id="Property.Update.RoomTypes.Name">…</update>
<delete id="Property.Delete.RoomTypes.One">…</delete>
```

- **参数用 `@Name`**（和匿名对象/实体的属性名对应），Dapper 负责映射，**不要拼字符串**（SQL 注入）。
- 可选条件用 `(@X IS NULL OR [Col] = @X)`。
- 每条 SQL 自带分号结尾；**一条 SQL 一个元素**，不要塞两条。
